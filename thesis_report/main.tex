    % Abstract content
    Enforcing \textbf{information flow security} in concurrent programs is difficult. Points of public observation (I/O operations, synchronisation and stalling for example) may be dependent upon secret information. Differences in execution time, and reordering of execution caused by dependence on secret information allows an adversary to discover secret information. Axiomatic approaches, such as \textbf{leaky assertions} using \textbf{Owicki-Gries} reasoning, allow mathematical proof of information leakage through a point of public observation. However, finding vulnerable points and proving information leakage manually in complex programs is tedious, error-prone and impractical.

    This thesis combines information flow techniques with operational model checking. We translate the axiomatic leaky assertion approach to temporal safety properties expressed in \textbf{TLA+ (Temporal Logic of Actions)\slash PlusCal}. By adding extra clocks to capture timing information, the explicit model checker \textbf{TLC} is used to exhaustively check all possible thread interleavings. This allows us to confirm whether security properties hold in a program, and if not, to produce concrete counter-example traces showing information leaks.

    We evaluate our approach across six different benchmarks: semaphore synchronisation in shared memory, round-robin scheduling, branch padding defences, modular exponentiation in cryptography, timing channels during web authentication, and sequence locks in persistent memory. For all benchmarks, all reachable interleavings were checked in less than 730~ms. If any information leakage was possible in a vulnerable system, TLC found safety violations, and generated detailed counter-example traces showing the interleaving orders that caused information leakage. Within mitigated programs, TLC confirmed that on no reachable paths was information leaked. This demonstrates an automatic approach to find timing channels within concurrent software and validate mitigation strategies.

\chapter{INTRODUCTION}
\enlargethispage{1.5\baselineskip}

\section{Background}
Modern multi-threaded software relies on concurrent execution across shared memory address spaces, coordinating via synchronization primitives like mutexes and semaphores. Ensuring information flow security in these systems is fundamentally challenging because non-deterministic thread interleavings and shared-resource contention introduce subtle channels through which secret data can propagate.

\section{Problem Statement}
In concurrent programs, multiple threads often share resources such as memory, locks and semaphores. The way in which these threads are interleaved depends on the non-deterministic scheduling algorithm. However, it may be possible for information to be leaked by public events within the program, such as output, synchronisation and waiting. If the control flow of the program up to one of these public events depends on some secret (such as a secret key, or confidential bit of information $h$), the execution time and order of the threads will change depending on the value of this secret. By observing the difference in execution times, or the order of public events, it is possible to infer secrets that would not otherwise be revealed, using a timing channel.

To illustrate this concretely, consider the example in Figure~\ref{fig:motivating-example}. Two threads ($T_1, T_2$) compete for a binary semaphore \texttt{sem} (initial value: 1) and modify shared variable $v$ (initial value: 0). Depending on a secret bit $h \in \{0, 1\}$, thread $T_2$ may execute its critical section between public print statements \texttt{print('c')} and \texttt{print('d')}. If $h = 0$, $T_2$ skips its critical section, terminating quickly ($\Delta \le 3$ steps); if $h = 1$, $T_2$ contends behind $T_1$ ($\ge 7$ steps). By observing execution latency or output order, an attacker can infer $h$.

Although information leaks at public program points can be formally proved insecure using an axiomatic approach (\emph{leaky assertions}), current techniques require manual proofs. Locating vulnerability points, finding appropriate invariants and proving that all thread interleavings do not leak information is very time consuming, error prone and not scalable. Manual proofs cannot automatically explore the concurrent program state space. They cannot also produce concrete counterexample executions of leaking schedules or verify mitigation solutions.

In this thesis we solve this problem. We translate leaky assertions to temporal safety properties in TLA+/PlusCal and allow the explicit model checker TLC to automatically detect timing leaks. Counterexample executions can be produced, and mitigation solutions can be verified to be secure for all reachable thread interleavings.

\section{Research Scope and Objectives}
\enlargethispage{1.5\baselineskip}
This thesis links deductive information flow analysis to explicit-state model checking in order to find and confirm mitigations to side-channel leaks in systems. This thesis has four concrete aims:
\begin{enumerate}[label=\arabic*., itemsep=0.04em, topsep=0.04em]
    \item \textbf{Semantic Properties}: Prove the semantic link between Owicki--Gries interference-freedom, auxiliary clocks, and leaky assertions. Demonstrate interference-freedom ensures attacker deductions are preserved under all feasible execution paths (Proposition~3.1).
    \item \textbf{Identification}: Using dynamic labelling and the Readers--Writers Flow Model (RWFM), determine the public observation points which may be influenced by secret branches in the program and state modifications.
    \item \textbf{Multi-Layer Invariants and Verification}: Create a multi-layer invariant structure (functional correctness, calibration/leaky invariants, non-interference properties) to provide two forms of verification in TLC. Interleaving-agnostic verification can be performed (Mode~A) to prove deductive soundness, and diagnostic counterexample traces can be found (Mode~B).
    \item \textbf{Application and Mitigation Verification}: Six benchmark examples have been created, including concurrent synchronization, internal timing channels, algorithmic side channels, web services, and crash-consistent persistent memory. Within these examples, mitigations were proposed and verified to ensure they remove the covert channels.
\end{enumerate}
Within this work, observations, assertions, and models were manually created to provide rigorous proof of the key concepts and verification within this work. This creates a proven base from which tools can be developed in the future.

\chapter{LITERATURE REVIEW AND PRELIMINARIES}

\section{Temporal Logic of Actions (TLA+) by Leslie Lamport}

\subsection{TLA+ Formalism and Concurrency Modeling}
Temporal Logic of Actions (TLA+)~\cite{lamport2002specifying} uses set theory and first-order logic to specify concurrent and distributed systems. A system is specified via:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Initial State Predicate}: $Init$, defining valid starting states.
    \item \textbf{Next-State Relation}: $Next$, specifying permitted state transitions.
    \item \textbf{Temporal Property}: Canonical formula $Spec \triangleq Init \land \Box[Next]_{vars} \land \text{Fairness}$.
\end{itemize}
TLA+ provides three key modeling capabilities for our verification workflow:
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Precise Concurrency Semantics}: Accurately captures concurrency \\ (non-deterministic thread execution, semaphores/locks, and race conditions) without interference from operating system noise.
    \item \textbf{Non-Intrusive Timing Instrumentation}: Additional timing clocks ($t, T_{\text{start}}, t_{\text{prime}}$) and observable variables can be added without affecting the functionality of the program.
    \item \textbf{Automatic Verification}: Replaces complex manual proofs (Owicki--Gries proofs) with push-button automatic verification.
\end{itemize}

\subsection{PlusCal Algorithmic Language}
PlusCal is an imperative algorithmic specification language that can be compiled directly into standard TLA+. The language contains familiar imperative language features (processes, loops, branching, and \texttt{await} statements) to help specify concurrent software. To produce effective models, guidelines are provided by Wayne~\cite{wayne2018practical} for structuring PlusCal processes, state variables, and invariant properties. Each line (or label) in PlusCal corresponds to an atomic step in execution. As such, during verification with TLC, two processes can only be interleaved at line boundaries. This gives fine control over when context switches occur and how race conditions arise.

\subsection{The TLC Model Checker and Experimental Verification}
TLC is an explicit-state model checker. It performs a breadth-first search on all reachable states from the initial state ($Init$). Deadlock and invariant properties are analysed throughout the state space. Within this project, information leakage and mitigations have been verified in two modes within TLC:
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{In Mode A}: Verifies the attacker's calibrated leaking property ($\text{Observed} \implies (A \iff h = \text{secret})$) across all reachable states. If no violations occur, it has been proved mathematically valid in all possible thread executions.
    \item \textbf{In Mode B}: The security property \texttt{NoTimingLeak} is checked. If there is information leakage, model checking will stop immediately and a shortest counterexample will be produced to show the path through the model and the timing difference in the execution path that causes the secret to be leaked.
    \item \textbf{Mitigated Model}: Finally, in the mitigated model (with potential mitigations, such as branch padding, dummy operations, or memory flushing), verification confirms that 0 violations occur and that the channel has been closed.
\end{itemize}

\section{An Axiomatic Approach to Detect Information Leaks in Concurrent Programs}
Security in information flow ensures non-interference, so that secrets (high) do not influence public outputs (low). However, in concurrent programs, requiring strict non-interference can be too restrictive.

\subsection{Limitations of Non-Interference in Concurrency}
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Too Many False Positives}: Multi-threading can lead to non-deterministic timing variations using locking mechanisms and semaphores. Tools enforcing non-interference may produce many false negatives.
    \item \textbf{Leaky Assertions}: Instead of enforcing strict non-interference, Ghosal and Shyamasundar~\cite{ghosal2021axiomatic} introduce the concept of leaky assertions, which allow the identification of targeted leaks in a program. Here, public observations directly reveal secrets.
\end{itemize}

\subsection{Definition and Mechanics of Leaky Assertions}
\begin{definition}[Leaky Assertion]
A Leaky Assertion occurs at public observation location $\ell$. Observation of assertion $A$ reduces uncertainty in the value of secret variable $h$. Given a set $H$ of possible secret values, an assertion $A$ is leaky when the set of secret values consistent with the observation of assertion $A$ is a proper subset of $H$ (the deduction of secret values):
\begin{equation}
    H_{\text{deduced}} = \{ h \in H \mid \mathrm{Post}(\ell, h) \implies A \} \subsetneq H
\end{equation}
If $|H_{\text{deduced}}| = 1$ then it is possible to exactly deduce the value of the secret.
\end{definition}

\subsection{Auxiliary Clocks and Timing Channels}
Timing variables are added to allow side-channel analysis without changing program functionality:
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Timing Analysis}: A start time ($T_{\text{start}}$) is recorded when entering the program. A timing variable ($t$) increments with every step in the program. A finish time ($t_{\text{prime}}$) is recorded when exiting the program at a public statement.
    \item \textbf{Deduction}: If the secret is taken to be true, causing contentions in locks or increasing the number of operations, the time it takes to execute $\Delta = t_{\text{prime}} - T_{\text{start}}$ can be used to detect the secret. If $\Delta < \Delta_{\text{thresh}}$ then $(\text{Observed} \land \Delta < \Delta_{\text{thresh}}) \implies (h = 0)$. If $\Delta \ge \Delta_{\text{thresh}}$ then $(\text{Observed} \land \Delta \ge \Delta_{\text{thresh}}) \implies (h = 1)$.
    \item \textbf{Automatic Verification}: In~\cite{ghosal2021axiomatic}, these assertions were only manually proven. This thesis has been implemented as an automatic TLA+ model, and verified for all interleavings using the TLC tool.
\end{itemize}

\section{Concepts of Hoare Triples and Mathematical Foundations}
Hoare logic~\cite{hoare1969axiomatic} provides the formal mathematical foundation for reasoning about program correctness through assertions and pre-/postcondition contracts.

\subsection{The Hoare Triple and Notions of Correctness}
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{The Hoare Triple ($\{P\}\, S \,\{Q\}$)}:
    \begin{itemize}[itemsep=0.15em]
        \item $P$ (\emph{Precondition}): An assertion over program variables that must hold before executing statement $S$.
        \item $S$ (\emph{Statement}): The program command or atomic action to be executed.
        \item $Q$ (\emph{Postcondition}): A postcondition guaranteed to hold at the end of $S$ assuming termination.
    \end{itemize}
    \item \textbf{Partial and Total Correctness}:
    \begin{itemize}[itemsep=0.15em]
        \item \emph{Partial Correctness} ($\models_{\text{par}} \{P\}\, S \,\{Q\}$): Guarantees that the postcondition $Q$ holds once execution has finished. It does not guarantee that execution will finish.
        \item \emph{Total Correctness} ($\models_{\text{tot}} \{P\}\, S \,\{Q\}$): Guarantees that execution will finish and at the end of execution $Q$ is true in the new state.
    \end{itemize}
    Partial correctness ensures that the state is invariant under program execution within side channels. Model checking ensures reachability and termination.
\end{itemize}

\subsection{Core Inference Rules}
Hoare logic provides compositional rules for deriving program properties step-by-step:
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Axiom of Assignment}: $\{P[e/x]\}\, x := e \,\{P\}$, replacing free occurrences of $x$ in $P$ with expression $e$.
    \item \textbf{Sequential Composition}: Chains consecutive statements by matching intermediate assertions ($\{P\}\, S_1 \,\{Q\}$ and $\{Q\}\, S_2 \,\{R\} \implies \{P\}\, S_1; S_2 \,\{R\}$).
    \item \textbf{Conditional Execution}: Analyzes branch paths under their respective path conditions ($\{P \land B\}\, S_1 \,\{Q\}$ and $\{P \land \neg B\}\, S_2 \,\{Q\}$).
    \item \textbf{Rule of Consequence}: Allows strengthening preconditions ($P \implies P'$) or weakening postconditions ($Q' \implies Q$).
    \item \textbf{Loop Invariance}: A condition $I$ that is true before, during, and after execution of each loop iteration ($\{I \land B\}\, S \,\{I\}$).
\end{itemize}

\subsection{Weakest Preconditions and Verification Conditions}
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Weakest Precondition ($\mathrm{wp}(S, Q)$)}: The strongest precondition that guarantees termination and that the postcondition $Q$ holds after execution of $S$.
    \item \textbf{Verification Conditions}: To verify that a program satisfies contract $\{P\}\, S \,\{Q\}$, it must be possible to prove that:
    \begin{equation}
        P \implies \mathrm{wp}(S, Q)
    \end{equation}
    This principle allows assertions to be used to verify safety conditions in programs.
\end{itemize}

\section{An Axiomatic Proof Technique for Parallel Programs}
Owicki and Gries~\cite{owicki1976axiomatic} extended Hoare logic to concurrent programs communicating through shared variables.

\subsection{Sequential Proof Outlines to Parallel Composition}
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Sequential Proof}: In a sequential proof, the invariant holds between each statement of the program ($\{P_0\}\, S_1 \,\{P_1\} \dots S_m \,\{P_m\}$). Each step adheres to standard Hoare logic rules.
    \item \textbf{Parallel Concurrency Failure}: In concurrent programs ($S = \textbf{cobegin } S_1 \parallel \dots \parallel S_n \textbf{ coend}$), proving individual threads in isolation is insufficient. Interleaved steps from peer threads can mutate shared memory and invalidate intermediate assertions.
\end{itemize}

\subsection{Interference Freedom and Auxiliary Variables}
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Interference Freedom}: An invariant, $P$, in thread $S_1$ is interference-free with respect to an atomic block, $T$, in thread $S_2$ if:
    \begin{equation}
        \{P \land \mathrm{pre}(T)\}\, T \,\{P\}
    \end{equation}
    If all statements in all threads are interference-free with all invariants in all other threads, then the parallel combination is provably correct.
    \item \textbf{Auxiliary Variables}: Sometimes it is necessary to introduce auxiliary variables in order to track execution. These must:
    \begin{itemize}[itemsep=0.15em]
        \item Be assigned in the form $a := e$. They cannot be referenced in conditionals in branches, loops, and assignments to program variables.
        \item Track information about the execution of the program, the state of the threads, or time. However, they do not change the state transitions of the program.
    \end{itemize}
\end{itemize}

\subsection{Scalability Limitations of Manual Proofs}
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Combinatorics}: If there are $n$ threads, each with $m$ atomic statements, $O(n^2 \cdot m^2)$ verification conditions must be checked manually to ensure interference freedom.
    \item \textbf{Model Checking}: Within a concurrent program containing loops, locks, and auxiliary clocks, manually verifying correctness can quickly become long-winded and error-prone. To overcome this issue, models can be written in TLA+. The tool TLC can then be used to automatically verify the model.
\end{itemize}

\section{Dynamic Labelling and Readers--Writers Flow Model (RWFM)}
Dynamic Labelling and the \emph{Readers--Writers Flow Model (RWFM)}~\cite{ghosal2018secrypt,ghosal2020dbsec} track information flow during execution without requiring rigid static security lattices:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Entity Labels}: Every entity $x$ is assigned a label triple $(s_x, R_x, W_x)$, specifying owner $s_x$, readers $R_x$, and writers $W_x$.
    \item \textbf{Permissible Flow Policy}: Information flows securely from $x$ to $y$ iff confidentiality ($R_x \supseteq R_y$) and integrity ($W_x \subseteq W_y$) hold.
    \item \textbf{Dynamic Context Promotion}: If a conditional branch is taken on the secret, the current context will be promoted ($\lambda(pc) = \top$) and any shared synchronization variables within this branch will be tainted with the secret ($W_{\text{shared}} \leftarrow W_{\text{shared}} \cup \{\text{Secret}\}$).
    \item \textbf{Observation Point Identification}: Where contention occurs on secret-tainted variables, timing differences can be observed. By applying the RWFM rules, observation points can be identified in the public part of the program ($R = P$) for automatic model checking using TLA+\slash TLC.
\end{itemize}

\subsection{Statement Classification and Observation Point Identification}
To determine public statements that could leak covert timing or ordering information in a concurrent program, we consider the control flow and shared state. Each statement can be classified by its functionality, whether it is executed in a confidential context (i.e., after a conditional branch on the secret), and whether it modifies shared synchronization variables:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Process $T_1$ (Public)}: Contains public synchronization guards ($l_0: \texttt{await } sem > 0$), semaphore decrements and increments ($l_1, l_5$), observable outputs ($l_2: \texttt{print('a')}, l_4: \texttt{print('b')}$), and non-secret variable updates ($l_3: v = v + 1$). None of $T_1$'s operations depend directly on confidential data.
    \item \textbf{Process $T_2$ (Confidential Dependent)}: \\ Begins at public statement $l_0: \texttt{print('c')}$ to create a start observation point ($T_{\text{start}}$). Statement $l_1: \texttt{if } h \texttt{ then}$ introduces a conditional branch dependent on secret value $h$.
    \item \textbf{Branch-Dependent Execution Paths}: When $h = 1$, $T_2$ contends with $T_1$ for shared semaphore \texttt{sem} ($l_2, l_3$), updates $v$ ($l_4$), and releases \texttt{sem} ($l_5$), incurring lock-contention latency. If $h$ equals 0, the critical section is skipped ($l_6: \texttt{skip}$), meaning execution of process $T_2$ ends rapidly.
    \item \textbf{Candidate Leaking Exit Point}: Both execution paths meet at public statement $l_7: \texttt{print('d')}$. As this occurs directly after the divergent execution time caused by the secret-dependent conditional branch, this makes it an effective observation point ($t'$, implemented as \texttt{t\_prime} in TLA+) for observing timing and ordering differences. Therefore, in this example, $l_0$ is designated as a candidate start observation point and $l_7$ is designated as a candidate exit observation point for automatic model checking through TLA+\slash TLC.
\end{itemize}

\chapter{METHODOLOGY}

\section{Verification Framework and Workflow}
This verification approach allows us to identify side-channel leaks in a concurrent system, formally prove the correctness of inferences performed by an attacker, and verify that countermeasures are effective. To do so, we translate the high-level concurrent algorithm into a formal specification and perform exhaustive state exploration with the model checker TLC. Our end-to-end verification method follows five distinct stages:
\begin{enumerate}[label=\textbf{Stage \arabic*:}, leftmargin=1.9cm, itemsep=0.2em, topsep=0.15em]
    \item \textbf{Initial Observation Point Identification}: Using the RWFM methodology (Section~2.5), we first consider the concurrent program. By identifying the statements where secret-sensitive values influence branching and change shared synchronization variables in the system, we identify potential observation points. These include potential start ($l_0: \texttt{print('c')}$) and end ($l_7: \texttt{print('d')}$) points for observation leaks to occur.
    \item \textbf{PlusCal Modeling}: We model the concurrent threads as PlusCal processes interacting through shared memory. We assign explicit labels to the statements within the algorithm at key points in order to identify atomic execution blocks.
    \item \textbf{Auxiliary Side-Channel Instrumentation}: We augment the specification with auxiliary clock variables ($t, T_{\text{start}}, t'$ [represented by variable \texttt{t\_prime} in TLA+]) and an output sequence ($\texttt{out}$) to measure timing differences and event orderings without perturbing program control flow.
    \item \textbf{Layered Invariant Formulation}: We specify three complementary invariant layers: functional correctness, calibration and leaky assertions (soundness of attacker deductions), and security non-interference properties.
    \item \textbf{Two-Stage Verification with TLC and Countermeasure Validation}: We run the model checker TLC for all reachable states in the system across two verification modes:
    \begin{itemize}[itemsep=0.1em, topsep=0.1em]
        \item \emph{Mode A (Soundness)}: Proves attacker deductions hold across all possible execution schedules (0 violations).
        \item \emph{Mode B (Leak Discovery)}: Refutes non-interference and extracts diagnostic counterexample traces demonstrating exactly how a schedule leaks data.
        \item \emph{Countermeasure Validation}: Ensures that potential countermeasures (such as branch padding and memory barriers) prevent side-channel leaks, producing 0 violations.
    \end{itemize}
\end{enumerate}

\section{PlusCal Algorithm Modeling and Label Granularity}
The specification is written in PlusCal (based on C syntax). It is automatically translated to TLA+.

\subsection{Process Structure and Shared State}
Concurrent process models in our benchmarks given in Figure~\ref{fig:motivating-example} share global state and use secrets. We represent concurrent programs by multiple PlusCal processes. Processes are declared as:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Multiple Processes}: For each concurrent thread in the program, a separate process is defined (\texttt{process T1 = 1} and \texttt{process T2 = 2}). Each process has its own local variables and program counter ($pc$).
    \item \textbf{Secrets}: Non-deterministically, each secret variable takes a value in the set of possible values ($h \in \{0, 1\}$). Therefore, in the initial state, all possible assignments of secrets are explored in parallel by TLC.
    \item \textbf{Synchronization}: Global locks, semaphores, and condition variables are modeled using \texttt{await} statements. These cause execution to pause in a thread until the predicate evaluates to true. For example, \texttt{await sem > 0; sem := sem - 1;}.
\end{itemize}

\subsection{Label Granularity and Interleaving Semantics}
Atomic steps in PlusCal are indicated by labels:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Atomic Transitions}: Between two labels, all code is executed as one atomic transition.
    \item \textbf{Context Switches}: A context switch between processes can only occur at labels. If labels are placed between each statement in the program ($l_0, l_1, l_2, \dots$), then all possible interleavings and race conditions that may occur in a preemptive multicore system are checked by TLC.
\end{itemize}

\section{Auxiliary Instrumentation for Side Channels}
To observe execution time and event ordering without altering functional program behavior, we instrument the PlusCal models with auxiliary variables.

\subsection{Non-Invasive Instrumentation Rules}
Following classical auxiliary variable principles (Owicki--Gries and Lamport), the auxiliary variables do not occur:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item In assignment statements on the right-hand side in the form $x := e$ (where $x$ is a functional program variable).
    \item As part of boolean conditions, loop guard conditions, or assignments to functional variables.
\end{itemize}
Hence, they do not affect what functional states are reachable, nor how the threads will be scheduled.

\subsection{Measurable Side-Channel Quantities}
The following four forms of auxiliary variables can be found in each benchmark:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Global Virtual Time ($t$)}: Integer variable, initialised to $0$. The value is incremented by $1$ for every atomic statement executed by any thread. So it can be considered to be a measure of the amount of time passed during execution of the system.
    \item \textbf{Entry Time ($T_{\text{start}}$)}: Recorded at entry points of interest, e.g., $l_0: T_{\text{start}} := t$. The recording occurs when the process being observed begins to execute.
    \item \textbf{Exit Time ($t'$)}: Recorded at exit points of interest, e.g., $l_7: t' := t$ (represented by the variable \texttt{t\_prime} in the TLA+ specification). The recording occurs just before the public observable statement is executed (e.g., \texttt{print("d")} in this example).
    
    The difference between these values, $\Delta \triangleq t' - T_{\text{start}}$, represents how many time units were taken between entering and exiting the program, and so includes delays due to synchronisation and any additional loops caused by the secret information.
    \item \textbf{Public Output ($\texttt{out}$)}: A list of strings, initialised to the empty list ($\langle \rangle$), which is appended with tokens to reflect public observable outputs. For example, $\texttt{out} := \text{Append}(\texttt{out}, \text{"c"})$.
\end{itemize}

\section{Layered Invariant Formulation}
We divide our invariant conditions into three layers for separation of concerns.

\subsection{Layer 1: Functional Correctness Invariants}
Prior to looking for leaks, we ensure that the program meets its desired functional behaviour:
\begin{itemize}[itemsep=0.15em, topsep=0.15em]
    \item \textbf{Type Safety (\texttt{TypeOK})}: We ensure that program variables take values within their mathematical domains ($\texttt{sem} \in \{0, 1\}$, $t \in \mathbb{N}$, $pc \in [\text{ProcSet} \to \text{Labels}]$).
    \item \textbf{Structural Invariants (\texttt{GlobalInv})}: Validates shared-memory safety contracts such as mutual exclusion:
    \begin{equation}
        \texttt{sem} + (\text{if } pc[1] \in \text{T1Crit} \text{ then } 1 \text{ else } 0) + (\text{if } pc[2] \in \text{T2Crit} \text{ then } 1 \text{ else } 0) = 1
    \end{equation}
    This ensures that only one process is in the critical region at any point in time.
    \item \textbf{Functional Postcondition (\texttt{FunctionalPost})}: We ensure that when the program terminates, the program variables have computed the correct output ($v = 1 + 2h \land \texttt{sem} = 1$).
\end{itemize}

\subsection{Layer 2: Calibration and Leaky Assertions (Soundness)}
This layer formalizes the attacker's deductions based on public measurements. To systematically construct these assertions, we bridge the axiomatic Hoare logic foundations (Sections~2.3 and 2.4) with our TLA+ specification:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Path Proof Outlines and Postconditions}: At candidate entry point $l_0$, the auxiliary clock is recorded ($T_{\text{start}} := t$). Program execution diverges based on the secret condition ($h = 0$ vs $h = 1$). Along each execution path $\pi_v$ for secret $h = v$, sequential Hoare composition ($\{P_i\}\, S_i \,\{P_{i+1}\}$) yields a path postcondition over elapsed time $\Delta \triangleq t' - T_{\text{start}}$ at exit point $l_7$:
    \begin{equation}
        \{T_{\text{start}} = t_0 \land h = v\} \; \pi_v \; \{t' - t_0 \in [\Delta_{\min}^{(v)}, \Delta_{\max}^{(v)}]\}
    \end{equation}
    where $[\Delta_{\min}^{(v)}, \Delta_{\max}^{(v)}]$ represents the latency bounds reachable under secret value $v$.
    
    \item \textbf{Interference-Freedom and Calibration Bounds (\texttt{Calib0}, \texttt{Calib1})}: In concurrent execution, peer threads interleave and mutate shared variables. Rather than manually proving $O(n^2 \cdot m^2)$ Owicki--Gries interference-freedom conditions ($\{P \land \mathrm{pre}(T)\}\, T \,\{P\}$), we mechanize these path postconditions into calibration invariants:
    \begin{align*}
        \texttt{Calib0} &\triangleq (\texttt{Observed} \land h = 0) \implies \Delta \in [\Delta_{\min}^{(0)}, \Delta_{\max}^{(0)}] \\
        \texttt{Calib1} &\triangleq (\texttt{Observed} \land h = 1) \implies \Delta \in [\Delta_{\min}^{(1)}, \Delta_{\max}^{(1)}]
    \end{align*}
    TLC model checking in Mode~A automatically explores all reachable thread interleavings, verifying that these reachability intervals hold without exception.

    \item \textbf{Axiomatic Leaky Inference Rules and TLA+ Encoding (\texttt{LA\_*})}: When reachability intervals are disjoint across secret choices, the attacker deduces the secret through formal axiomatic inference rules:
    \begin{gather}
        \frac{[at\_l_0] : t = T \quad [at\_l_7] : t = t' \quad t' - T \ll \Delta t}{h = 0} \\[1.0ex]
        \frac{[at\_l_0] : t = T \quad [at\_l_7] : t = t' \quad t' - T \ge \Delta t}{h = 1}
    \end{gather}
    These inference rules formalize the deduction of secret $h$ from observable duration $\Delta \triangleq t' - T$. In our framework, we mechanize these deduction rules as executable temporal safety invariants:
    \begin{align*}
        \texttt{LA\_Low}   &\triangleq (\texttt{Observed} \land \Delta < \Delta_{\text{lo}}) \implies (h = 0) \\
        \texttt{LA\_High}  &\triangleq (\texttt{Observed} \land \Delta \ge \Delta_{\text{hi}}) \implies (h = 1) \\
        \texttt{LA\_Trace} &\triangleq \texttt{ACDB} \implies (h = 0)
    \end{align*}
    Verifying these invariants in Mode~A formally proves that whenever an attacker observes these public events, their deduction of the secret is mathematically sound.
\end{itemize}

\subsection{Layer 3: Security Invariants (Non-Interference)}
To test whether the program is vulnerable to information leaks, we specify non-interference security properties asserting that public observations are invariant to secret inputs:
\begin{itemize}[itemsep=0.15em, topsep=0.15em]
    \item \textbf{Timing Indistinguishability (\texttt{NoTimingLeak})}: Asserts that elapsed duration $\Delta$ falls strictly within the safe overlapping range where the attacker cannot distinguish $h = 0$ from $h = 1$:
    \begin{equation}
        \texttt{NoTimingLeak} \triangleq \texttt{Observed} \implies (\Delta \ge \Delta_{\text{lo}} \land \Delta < \Delta_{\text{hi}})
    \end{equation}
    \item \textbf{Order Indistinguishability (\texttt{NoOrderLeak})}: Asserts that leaking output order patterns (e.g., \texttt{ACDB}) are never produced:
    \begin{equation}
        \texttt{NoOrderLeak} \triangleq \neg \texttt{ACDB}
    \end{equation}
\end{itemize}

\section{TLC Model Checker Execution and Trace Interpretation}
For each benchmark, we verify a set of invariants using TLC in different modes.

\subsection{Configuration and Execution Modes}
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Mode A (Soundness Check)}: Verifies invariants for Layer~1 functionality, calibration parameters, and leaky invariants (\texttt{TypeOK}, \texttt{GlobalInv}, \texttt{FunctionalPost}, \texttt{Calib}, \texttt{LA\_*}). If the verification returns `PASS' with zero errors, we can guarantee that given any order of thread execution, if the public observable is \texttt{TRUE} then the attacker can deduce the correct secret value.
    \item \textbf{Mode B (Leak Discovery)}: Verifies Layer~1 functional invariants alongside Layer~3 security invariants (\texttt{TypeOK}, \texttt{GlobalInv}, \texttt{NoTimingLeak}, \texttt{NoOrderLeak}). If the verification returns `FAIL', meaning the non-interference property is violated, a diagnostic trace showing a leak is outputted.
    \item \textbf{Mitigated Mode}: Security invariants are verified with mitigations in place (\texttt{Fixed = TRUE}). If the verification returns `PASS' (zero errors), we can formally confirm that the proposed mitigations prevent leakage from occurring in any order of thread execution.
\end{itemize}

\subsection{Interpreting Diagnostic Counterexample Traces}
If any security invariant fails in Mode B, information about the number of states reached is given. For example, in the concurrent synchronisation benchmark, 44 states (39 unique states, max depth of 5) are explored. The trace leading to the failure is provided below:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Step 2 ($l_0$)}: Process 2 runs statement $l_0$. The time that Process 2 entered the step is recorded ($T_{\text{start}} := t$) and $t$ increases to 1. The output of Process 2 becomes: $\texttt{out} = \langle \text{"c"} \rangle$. The state of $pc[2]$ becomes ``l1''.
    \item \textbf{Step 4 ($l_6$)}: Process 2 runs statement $l_6$. The time $t$ increases to 2, and the state of $pc[2]$ changes to exit state $l_7$.
    \item \textbf{Step 5 ($l_7$)}: Process 2 runs statement $l_7$. The time Process 2 exited the step is recorded as $t' = 2$ (\texttt{t\_prime} $= 2$). The time $t$ increases to 3. An additional character is added to the output, $\texttt{out} = \langle \text{"c"}, \text{"d"} \rangle$, and the state of $pc[2]$ changes to ``Done''.
\end{itemize}

As the secret path was not taken ($h = 0$), Process 2 ran in 2 ticks. If the secret path had been taken ($h = 1$), Process 2 would have had to acquire the shared semaphore \texttt{sem} and would therefore take 4 ticks (or more) to complete ($\Delta \ge 4$). As the difference in execution times between the two secret values is less than the lower bound ($\Delta < \Delta_{\text{lo}}$), the invariant \texttt{NoTimingLeak} is violated. The developer can follow this trace to see precisely where the timing leak is occurring (see Subsection~\ref{subsec:diagnostic-trace-walkthrough} for the step-by-step trace walkthrough and TLC GUI diagnostic output).

\subsection{Mitigation Verification Workflow}
Once an error trace has been found, possible mitigations (for example padding or memory barriers) can be added to the specification, depending on the setting of the boolean (\texttt{Fixed = TRUE}). By re-verifying with Mode B, we can confirm that:
\begin{enumerate}[label=\arabic*., itemsep=0.15em, topsep=0.15em]
    \item The security invariant (\texttt{NoTimingLeak}/\texttt{NoOrderLeak}) passes (0 errors).
    \item The explored state space has confirmed that execution times are equalised between all secret values. Therefore no side-channel is present.
\end{enumerate}

\section{Verification Process and Tool Environment}
PlusCal, TLA+, and TLC are used for verification:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{PlusCal}: All benchmarks were created in PlusCal, written with a syntax similar to C. Techniques discussed in~\cite{wayne2018practical} by Wayne have been applied during modelling. PlusCal allows imperative programming features (multiple threads, loops, conditions, and \texttt{await} statements) to be used, which are then translated into TLA+. Atomic step boundaries between labels allow for precise thread interleaving.
    \item \textbf{Temporal Logic of Actions (TLA+)}: Transitions between states are expressed in mathematical terms. Unprimed variables indicate the current state, and primed variables indicate the next state. This ensures clear meaning for each action.
    \item \textbf{TLC Model Checker}: A state-space model checker. All reachable states in the system are checked in breadth-first order. Safety invariants are checked at each state. If any invariant fails, the shortest trace to produce the failure will be displayed.
    \item \textbf{Environment}: TLC was executed on Java 11 on macOS. For each benchmark, a configuration file contains the constants, initial states, and desired invariants. Models were written in VS Code with the TLA+ extension. Batch verification was performed using the TLC command line.
\end{itemize}

\section{Limitations and Assumptions}
We note the following boundaries and assumptions in our verification methodology:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Manual Translation}: The algorithm for each benchmark was manually translated to PlusCal, and observations selected according to RWFM techniques. In future it would be useful to produce a front-end parsing tool to automatically translate source code into TLA+.
    \item \textbf{Partial Information Flow Concepts}: RWFM was applied to select relevant observations; however, the full multi-level lattice algebra was not implemented.
    \item \textbf{Bounded State Space}: As with all state-space model checkers, parameters must be bounded. Secret bit(s), loop numbers, and number of threads must be limited. Whilst this allows confirmation that, for these particular bounded parameters, there is no leakage in any thread interleaving, general inductive proof is required for unbounded thread numbers.
\end{itemize}

\section{Benchmark 1: Concurrent Synchronization and Order Channels}

\subsection{Problem Context and Research Origin}
This benchmark investigates secret-dependent lock contention in multi-threaded programs, originating from the study by Ghosal and Shyamasundar~\cite{ghosal2021axiomatic}. Two concurrent threads $T_1$ and $T_2$ contend for a shared binary semaphore (\texttt{sem}) and mutate shared variable $v$. Thread $T_2$ conditionally accesses the critical section depending on a confidential secret $h \in \{0, 1\}$.

\subsection{PlusCal Algorithm and Model Specification}
Listing~\ref{lst:concurrent-leak} presents the formal PlusCal algorithm for the concurrent semaphore benchmark, modeled in \texttt{ConcurrentLeak.tla}. The specification models two concurrent threads $T_1$ and $T_2$ synchronizing via shared semaphore \texttt{sem} and variable $v$, instrumented with auxiliary clock variables ($t, T_{\text{start}}$, and exit clock $t'$ declared as \texttt{t\_prime}) to measure execution duration without altering program logic.

\subsection{Leakage Mechanism and Secret Variables}
The benchmark exhibits both timing and ordering side channels:
\begin{itemize}[itemsep=0.08em, topsep=0.06em]
    \item \textbf{Secret Variable}: $h \in \{0, 1\}$ (High Security), determines whether Process~$T_2$ enters the critical region.
    \item \textbf{Timing Side Channel}: If $h = 0$, Process~$T_2$ does not enter the critical section in the semaphore and finishes quickly (execution time difference $\Delta$ between exit time $t'$ and entry time $T_{\text{start}}$ is $\Delta \le 3$). If $h = 1$, Process~$T_2$ has to wait for the semaphore to be released behind $T_1$ and experiences a long delay ($\Delta \ge 7$).
    \item \textbf{Ordering Side Channel}: The observable outputs in `\texttt{out}' differ depending on $h$. If $h = 1$, processes follow the ordering ``a'', ``c'', ``d'', ``b'' ($\langle \text{"a"}, \text{"c"}, \text{"d"}, \text{"b"} \rangle$). If $h = 0$, $T_2$ can leave earlier meaning the observable outputs may be in an alternative ordering, for example ``c'', ``a'', ``d'', ``b'' ($\langle \text{"c"}, \text{"a"}, \text{"d"}, \text{"b"} \rangle$).
\end{itemize}

\subsection{Layered Invariants and Leaky Assertions Formulation}
\enlargethispage{4.0\baselineskip}
To rigorously evaluate functional correctness, side-channel leakage, and attacker deduction, the specification in \texttt{ConcurrentLeak.tla} is structured into three formal layers of invariants, as defined in Listing~\ref{lst:concurrent-invariants}:
\begin{itemize}[itemsep=0.08em, topsep=0.06em]
    \item \textbf{Functional Invariants}: $\texttt{TypeOK}$ ensures variables take valid values within their mathematical domains. $\texttt{GlobalInv}$ enforces binary mutual exclusion across concurrent critical regions ($\texttt{sem} + \text{in\_crit}_1 + \text{in\_crit}_2 = 1$). $\texttt{FunctionalPost}$ asserts that upon termination, the functional computation computes the correct output ($v = 1 + 2h$) and restores $\texttt{sem} = 1$.
    \item \textbf{Observation Layer}: Evaluated at the public exit point where $\texttt{Observed} \triangleq (pc[2] = \text{"Done"})$ and duration $\Delta \triangleq t' - T_{\text{start}}$ (formulated in TLA+ as \texttt{Delta == t\_prime - T\_start}). Ordering predicate $\texttt{ACDB}$ checks whether public characters appear in order $\langle \text{"a"}, \text{"c"}, \text{"d"}, \text{"b"} \rangle$.
    \item \textbf{Calibration Bounds}: $\texttt{Calib0}$ and $\texttt{Calib1}$ establish baseline duration bounds under arbitrary thread interleavings: $\Delta \in [2, 7]$ when $h = 0$, and $\Delta \in [4, 9]$ when $h = 1$.
    \item \textbf{Attacker Leaky Assertions}: $\texttt{LA\_Low}$ and $\texttt{LA\_High}$ encode deduction of secret $h$ from thresholded execution duration $\Delta$, while $\texttt{LA\_Trace}$ deduces $h = 0$ upon observing sequence $\texttt{ACDB}$.
    \item \textbf{Security Invariants (Non-Interference)}: $\texttt{NoTimingLeak}$ and $\texttt{NoOrderLeak}$ express observational equivalence. TLC refutes these to generate counterexample traces.
\end{itemize}

\begin{lstlisting}[style=pluscalstyle, caption={TLA+ layered invariants and leaky assertions for ConcurrentLeak.}, label={lst:concurrent-invariants}]
(* ================= FUNCTIONAL LAYER ================= *)
T1Crit == {"T1_2", "T1_3", "T1_4", "T1_5"}
T2Crit == {"l4", "l5"}

    /\ v \in Nat
    /\ h \in {0, 1}

    /\ t_prime \in Nat
    /\ out \in Seq({"a", "b", "c", "d"})

                 + (IF pc[2] \in T2Crit THEN 1 ELSE 0) = 1

FunctionalPost == Terminated => (v = 1 + 2*h /\ sem = 1)

(* ================= OBSERVATION LAYER ================= *)

          THEN CHOOSE i \in 1..Len(out) : out[i] = x

        /\ Pos("d") < Pos("b")

(* ================= LEAKY ASSERTIONS & SECURITY ================= *)

\subsection{TLC Model Configuration and Verification Metrics}
The TLC model configuration sets execution bounds: $\Delta_{\text{lo}} = 4$ and $\Delta_{\text{hi}} = 8$.
\begin{itemize}[itemsep=0.15em, topsep=0.12em]
    \item \textbf{Mode A}: All functional properties and leaky assertions were verified correctly, for all 44 states in the model (39 unique states, diameter 5) in 571\,ms. No violations occurred, meaning mathematical soundness of the attacker's deduction was proved.
    \item \textbf{Mode B}: Security property \texttt{NoTimingLeak} was checked. Since execution times differ depending on secret values, this invariant was disproved and a counterexample was generated to demonstrate the leak.

\begin{itemize}[itemsep=0.25em, topsep=0.2em]
    \item \textbf{State 1 (Initial Conditions)}: The model was initialised with secret value $h = 0$. Semaphores and synchronisation variables were initialised to $\texttt{sem} = 1$ and $v = 0$. Other clocks were initialised as $t = 0$, $T_{\text{start}} = 0$ and $t' = 0$ (\texttt{t\_prime} $= 0$). Public observable output `\texttt{out}' was empty ($\texttt{out} = \langle \rangle$). Program counters were set as $pc = [\text{"T1\_1"}, \text{"l0"}]$, meaning both Thread~$T_1$ and Thread~$T_2$ are ready to be executed (Figure~\ref{fig:tlc-trace}(a)).
    
    \item \textbf{State 2 (Public Entry Point)}: Thread~$T_2$ performs the entry statement labelled $l_0$. The modified variables are: Process~$T_2$ sets its initial time stamp: $T_{\text{start}} = 0$, adds the first character in the observable output: $\texttt{out} = \langle \text{"c"} \rangle$, increases the global step counter: $t = 1$, and updates program counter: $pc[2] = \text{"l1"}$.
    
    \item \textbf{State 3 (Conditional Branch)}: Thread~$T_2$ is performing a conditional branch based on the value of secret $h$. As the value of $h = 0$, the condition \texttt{if h = 1} is false. The \texttt{else} statement is performed and program counter updates to $pc[2] = \text{"l6"}$. This is very important as the semaphore acquisition is completely skipped.
    
    \item \textbf{State 4 (Dummy Balancing Statement)}: Thread~$T_2$ performs the dummy balancing statement at line $l_6$. The global counter increases to $t = 2$, and the program counter updates to $pc[2] = \text{"l7"}$ (Figure~\ref{fig:tlc-trace}(b)).
    
    \item \textbf{State 5 (Public Exit Point)}: Thread~$T_2$ has reached the Public Exit Point. The time at which the process finishes is recorded in the clock $t' = 2$ (\texttt{t\_prime} $= 2$). The public character ``d'' is added to the output list: $\texttt{out} = \langle \text{"c"}, \text{"d"} \rangle$. The global counter increases to $t = 3$. The process finishes: $pc[2] = \text{"Done"}$. Notably, the program counter in Thread~$T_1$ remains at \text{"T1\_1"} (all 5 states). Therefore, pre-emptive scheduling allows Process~$T_2$ to finish without any context switches to Process~$T_1$.
\end{itemize}

\noindent\textbf{Deduction of Secret Values}:
Upon termination in State~5, condition \texttt{Observed} ($pc[2] = \text{"Done"}$) is met. As for non-interference, the execution time should be within the safe time bounds $\Delta \ge \Delta_{\text{lo}}$ ($\Delta_{\text{lo}} = 4$). Therefore, the invariant \texttt{NoTimingLeak} is false, meaning there is a timing leak. As $\Delta_{\text{obs}} = 2 < 4$, an external observer can deduce with 100\% certainty that $h = 0$. Therefore, the counterexample provides a full proof of information leakage.

\section{Benchmark 2: Round-Robin Internal Timing Covert Channel}

\subsection{Problem Context and Research Origin}
This example, modeled in the specification \texttt{InternalTiming.tla}, is based upon the work of Russo and Sabelfeld~\cite{russo2006closing}. Depending on the value of the Secret Variable, processes in multithreaded programs using Round-Robin scheduling exhibit a covert channel in execution time.

\subsection{Leakage Mechanism and Secret Variables}
Depending on the value of $h$, the number of times Thread~$T_2$ is executed changes. This means that the total execution time between START and END differs. If $h = 0$, total execution time $\Delta = 8$ steps. If $h = 1$, total execution time $\Delta = 9$ steps. An external observer can therefore directly deduce the value of secret $h$.

\subsection{Leaky Assertions Formulation}
Security Invariant Checked:
\begin{equation}
    \texttt{NoTimingLeak} \equiv \texttt{Observed} \implies \Delta = 8
\end{equation}
Attacker leaky assertions are formulated as $\text{LA\_High} \equiv (\text{Observed} \land \Delta = 9) \implies (h = 1)$ and $\text{LA\_Low} \equiv (\text{Observed} \land \Delta = 8) \implies (h = 0)$.

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec} \quad \textbf{Constants}: $\text{Fixed} \in \{\text{FALSE}, \text{TRUE}\}$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}, \texttt{MutualExclusion}
    \item \textbf{Mode A (Soundness)}: \texttt{Calib0}, \texttt{Calib1}, \texttt{LA\_Low}, \texttt{LA\_High}
    \item \textbf{Mode B (Leak Discovery)}: \texttt{NoTimingLeak}
\end{itemize}

\section{Benchmark 3: Branch-Padding Countermeasure and Constant-Time Execution}

\subsection{Problem Context and Research Origin}
Branch padding is a countermeasure proposed by Russo and Sabelfeld~\cite{russo2006closing} and generalised by Mantel and Starostin~\cite{mantel2015timing}, modeled in \texttt{Transformed.tla}. The goal is to mitigate the internal timing covert channel presented in Benchmark 2, by making the number of steps taken in branches equal.

\subsection{Mitigation Mechanism and Balanced Control Flow}
By inserting dummy balancing statements into the shorter branch, both execution paths take exactly the same number of scheduler turns regardless of secret $h$.

\subsection{Leaky Assertions and Mitigation Invariants}
Security Invariant Checked: $\texttt{NoTimingLeak} \equiv \texttt{Observed} \implies \Delta = 9$.

\subsection{TLC Model Configuration and Result}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec} \quad \textbf{Constants}: $\text{Fixed} = \text{TRUE}$
    \item \textbf{Result}: \textbf{PASS (No Errors)}. Therefore the timing channel has been mitigated.
\end{itemize}

\section{Benchmark 4: Cryptographic Modular Exponentiation Side Channel}

\subsection{Problem Context and Research Origin}
This example, modeled in the specification \texttt{ModSqLeaks.tla}, demonstrates a timing channel in the square and multiply algorithm for modular exponentiation ($b^e \bmod m$). This algorithm forms the basis of implementation of RSA and Diffie-Hellman. The vulnerability was originally identified by Kocher~\cite{kocher1996timing} and formulated axiomatically by Ghosal and Shyamasundar~\cite{ghosal2021axiomatic}.

\subsection{Leakage Mechanism and Secret Variables}
Timing Channel: Modulo squaring happens every iteration. However, modulo multiplication only occurs if the value of the secret bit $k[i] = 1$. An external observer can directly deduce the Hamming weight of the private key.

\subsection{Leaky Assertions Formulation}
Evaluated across bit index iterations $i \in 1..N$:
\begin{align*}
    \text{LA\_Mult\_Leak} &\equiv (\text{Observed} \land \text{StepMult}) \implies (k[i] = 1) \\
    \text{LA\_Hamming}   &\equiv (\text{Observed} \land \Delta = \text{Base} + c \cdot w) \implies (\text{HammingWeight}(k) = w)
\end{align*}
The security invariant is defined as $\text{NoTimingLeak} \equiv \texttt{Observed} \implies \forall w_1, w_2 : \Delta(w_1) = \Delta(w_2)$.

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec} \\
    \textbf{Constants}: $N = 4$ (key width), $\text{BaseCost} = 4$, $\text{MultCost} = 2$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}, \texttt{CorrectExp}
    \item \textbf{Mode A (Soundness)}: \texttt{LA\_Mult\_Leak}, \texttt{LA\_Hamming}
    \item \textbf{Mode B (Leak Discovery)}: \texttt{NoTimingLeak}
\end{itemize}

\section{Benchmark 5: Web Authentication Latency Side Channel}

\subsection{Problem Context and Research Origin}
This example, modeled in the specification \texttt{WebServiceLeak.tla}, demonstrates a timing channel in a web authentication endpoint. It follows the predictive mitigation scheme from Askarov, Zhang and Myers~\cite{askarov2010predictive}. The process checks whether or not a username exists. If a username does not exist, no cryptographic password verification occurs. If the username exists but the password is incorrect, expensive hashing occurs.

\subsection{Leakage Mechanism and Secret Variables}
\begin{itemize}[itemsep=0.1em, topsep=0.1em]
    \item \textbf{Secret Variables}: $\texttt{valid\_user} \in \{\text{TRUE}, \text{FALSE}\}$ (User account exists), and\\ $\texttt{password\_match} \in \{\text{TRUE}, \text{FALSE}\}$ (Correct password).
    \item \textbf{Timing Channel}: If the username does not exist ($\neg\texttt{valid\_user}$), then the server stops immediately after the database query. (Execution time $\Delta = 1$ (\text{LookupCost})). If the username exists but the password is incorrect, expensive password hashing occurs. (Execution time $\Delta = 11$ ($1 + 10 = \text{LookupCost} + \text{HashCost}$)). The messages returned in both cases are the same (``error message''). However, depending on how long the response takes, an external observer can determine if the user account exists.
\end{itemize}

\subsection{Leaky Assertions Formulation}
Evaluated at response point $l_{\text{exit}}$ where $\text{out}_{\text{err}} \equiv (\text{result} = \text{"error message"})$:
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item $\text{LA\_Time\_Low} \equiv (\neg\text{Fixed} \land \text{Observed} \land \text{out}_{\text{err}} \land \Delta \le 1) \implies (h = 0)$
    \item $\text{LA\_Time\_High} \equiv (\neg\text{Fixed} \land \text{Observed} \land \text{out}_{\text{err}} \land \Delta \ge 11) \implies (h = 1)$
    \item $\text{LA\_Timing} \equiv (\neg\text{Fixed} \land \text{Observed} \land \text{out}_{\text{err}}) \implies ((\Delta \ge 5) \iff (h = 1))$
    \item \textbf{Security Invariant}: $\text{NoTimingLeak} \equiv (\text{Observed} \land \text{out}_{\text{err}}) \implies (\Delta = 11)$
\end{itemize}

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec} \\
    \textbf{Constants}: $\text{LookupCost} = 1$, $\text{HashCost} = 10$, $\text{Threshold} = 5$, \\
    $\text{Fixed} \in \{\text{FALSE}, \text{TRUE}\}$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}, \texttt{FunctionalCorrect}
    \item \textbf{Mode A (Soundness)}: \texttt{Calib0}, \texttt{Calib1}, \texttt{LA\_Time\_Low}, \texttt{LA\_Time\_High}, and\\ \texttt{LA\_Timing}
    \item \textbf{Mode B (Leak Discovery)}: \texttt{NoTimingLeak}
\end{itemize}

\section{Benchmark 6: Persistent Memory Seqlock Under Power Failure}

\subsection{Problem Context and Research Origin}
This benchmark investigates information disclosure in non-volatile persistent memory architectures under power failure, based on the research by Graeme Smith~\cite{smith2026persistent} and modeled in \texttt{SeqLock.tla}. The protocol models a Linux reader-writer seqlock managing confidential and public data records.

\subsection{Leakage Mechanism and Secret Variables}
The system maintains persistent state variables: \texttt{pm\_x1} (Data), \texttt{pm\_x2} (Classification) and \texttt{pm\_c} (Sequence Counter).

If data ($x_1 = 1$) and sequence counter ($c$) are written to Persistent Memory during a crash, however the security class ($x_2 = 1$) is not written to persistent memory and is still in volatile memory, then memory will be in an inconsistent state after reboot. The sequence counter ($c$) will be even (quiescent) and the class ($x_2 = 0$) will show low classification. However, the data ($x_1 = 1$) will be high secret. After reboot, if a reader reads $x_2 = 0$ it will send a high secret value of 1 over the public channel.

\subsection{Leaky Assertions Formulation}
The security invariants are defined as:
\begin{align*}
    \text{LA\_PersistentLeak} &\equiv (\neg\text{Fixed} \land \text{crashed} \land \text{ReaderDone} \\
    &\qquad \land (\exists k : \text{out}[k] = 1)) \implies (h = 1) \\
    \text{NoInformationLeak} &\equiv \forall k \in 1..\text{Len}(\text{out}) : (\text{out}[k] = 1) \implies (h = 0)
\end{align*}

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec} \quad \textbf{Constants}: $\text{Fixed} \in \{\text{FALSE}, \text{TRUE}\}$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}
    \item \textbf{Mode A (Soundness)}: \texttt{LA\_PersistentLeak}
    \item \textbf{Mode B (Leak Discovery)}: \texttt{NoInformationLeak}
\end{itemize}

\section{Performance Summary and Observations}
Summary of model checking performance for all 6 benchmarks:
\begin{itemize}[itemsep=0.15em, topsep=0.1em]
    \item \textbf{Speed}: All benchmarks were checked in under 1 second (Fastest 466\,ms, slowest 729\,ms).
    \item \textbf{Size of State Space}: Number of states in state space varied between 3 (crash reboot seqlock) and 322 (modular exponentiation).
    \item \textbf{Dual Mode Checking}: Using Mode A it was confirmed that the attack deductions would occur for all possible interleavings. Using Mode B specific counter examples were generated showing exactly what scheduling of threads resulted in the information leak.
\end{itemize}

\chapter{CONCLUSION AND FUTURE WORK}
\enlargethispage{1.5\baselineskip}

\section{Conclusion}
This thesis provides a verification methodology for detecting information leakage and side-channel vulnerabilities in concurrent programs using TLA+. We provide executable invariants for leaky assertions, which enables verification of these properties through automated proof. Evaluation on 6 benchmarks showed that employing a 3-layered invariant structure with two modes of verification within TLC provides useful results:
\begin{itemize}[itemsep=0.12em, topsep=0.1em]
    \item \textbf{In Mode A}: We formally prove that, in all possible thread interleavings, given certain public observations (time-intervals, or sequences of events) the attacker can make correct deductions about the secret value in all cases, with no violations.
    \item \textbf{In Mode B}: We disprove non-interference properties and automatically generate explicit counter-example traces. These traces clearly show what thread orders and synchronisation delays caused information leakage in the program.
\end{itemize}
Finally, we verified that mitigations in software (branch padding, constant-time operations, and purging of caches in persistent memory) successfully remove side-channel vulnerabilities in all possible execution paths.

\section{Future Work}
The identification of observation points, insertion of atomic step annotations and leaky assertions in this work is performed manually. Future work involves \textbf{automation} of this verification and mitigation pipeline:

\begin{enumerate}[label=\arabic*., itemsep=0.15em, topsep=0.1em]
    \item \textbf{Automatic Translation of Source Code to PlusCal}:
    Develop an automated front-end (such as Clang/LLVM for C/C++, or Soot for Java) to translate concurrent source code. Each statement should be translated to corresponding actions in PlusCal, preserving atomicity annotations. Non-intrusive extra clocks ($t, T_{\text{start}}, t'$) and observable traces are inserted.

    \item \textbf{Automatic Leaky Assertion Synthesis}:
    Use static taint analysis and symbolic execution to automatically infer information flow from annotated secret variables to shared synchronisation. Observation points vulnerable to leaks can be identified, calibration intervals determined, and leaky assertions generated automatically.

    \item \textbf{Counterexample-Guided Automated Repair}:
    Develop tools to automatically parse error traces from TLC and synthesise targeted fixes. Cycle balancing branch padding or persistent memory fence instructions may be inserted into the source code.
\end{enumerate}
