\chapter{INTRODUCTION}

\section{Background}
Modern software relies heavily on concurrency. Multicore processors and distributed servers run multiple threads that share memory and coordinate through locks, semaphores, and condition variables.

However, concurrent execution introduces non-determinism: thread schedules vary based on hardware timing, operating system decisions, and resource contention. Even when a program computes correct results without crashing, the way threads interleave can leak private information.

These leaks typically occur through side channels like execution time or output ordering. If a thread takes a different branch or waits on a semaphore based on a secret value, an observer timing the operations or watching the order of outputs can reconstruct that secret. Catching these leaks requires formal methods that can inspect all possible interleavings rather than just testing a handful of runs.

\section{Problem Statement}
Leaky assertions provide a mathematical way to reason about information leaks in concurrent code. However, existing work relies entirely on manual Owicki--Gries proofs written by hand on paper. Writing these proofs by hand is slow, tedious, and prone to mistakes, especially as soon as programs contain loops, multiple shared variables, or fine-grained interleavings.

More importantly, hand proofs do not provide an executable verification process. They cannot explore state spaces automatically, produce counterexample traces that show developers exactly how a leak happens, or verify whether a proposed fix actually eliminates the leak. We need a way to turn leaky assertions into executable models that can be checked automatically.

\section{Research Scope and Objectives}
The primary objective of this thesis is to bridge deductive information-flow theory with automated explicit-state model checking to detect side-channel leaks and verify mitigations in concurrent and sequential software. To achieve this, the research pursues four concrete objectives:
\begin{enumerate}[label=\arabic*., itemsep=0.35em]
    \item \textbf{Theoretical Foundations}: Formalize the semantic relationship between Owicki--Gries interference freedom, auxiliary clock instrumentation, and leaky assertions, proving that interference freedom preserves attacker deductions along reachable execution paths (Proposition~3.1).
    \item \textbf{Observation Point Selection}: Apply dynamic labelling principles and the Readers--Writers Flow Model (RWFM) to identify candidate public observation points influenced by secret branches and shared-state updates.
    \item \textbf{Layered Invariant and Verification Methodology}: Develop a structured three-layer invariant hierarchy (functional correctness, calibration/leaky assertions, and non-interference security properties) supporting dual-mode verification in TLC: proving deductive soundness across all interleavings (Mode~A) and extracting diagnostic counterexample traces (Mode~B).
    \item \textbf{Empirical Evaluation and Mitigation Checking}: Model and evaluate six representative benchmark scenarios spanning concurrent synchronization, internal timing channels, algorithmic side channels, web services, and crash-consistent persistent memory, while formally verifying that proposed mitigations eliminate the covert channels.
\end{enumerate}
In this work, observation points, assertions, and models are constructed manually to rigorously prove the core concepts and verification mechanics, establishing a validated foundation for future automated toolchains.

\section{Chapter Overview}
The remainder of this thesis is structured as follows:
\begin{itemize}[itemsep=0.35em]
    \item \textbf{Chapter 2 (Literature Review and Preliminaries)}: Reviews foundational concepts: TLA+ and PlusCal, the axiomatic formulation of leaky assertions, Hoare logic, the Owicki--Gries proof technique for parallel programs, and dynamic labelling with RWFM.
    \item \textbf{Chapter 3 (Methodology)}: Describes the framework: selecting observation points with RWFM, writing PlusCal/TLA+ models with auxiliary clocks, and organizing layered invariants for dual-mode TLC checking.
    \item \textbf{Chapter 4 (Experiments and Results)}: Evaluates the approach on six benchmark models (semaphore contention, round-robin scheduling, branch-padding mitigation, cryptographic exponentiation, web login latency, and persistent memory seqlock), reporting state counts, counterexample traces, and mitigation checks.
    \item \textbf{Chapter 5 (Conclusion and Future Work)}: Summarizes findings, discusses practical modeling lessons, and presents directions for future work toward automated verification.
\end{itemize}

\chapter{LITERATURE REVIEW AND PRELIMINARIES}

\section{Temporal Logic of Actions (TLA+) by Leslie Lamport}

\subsection{TLA+ Formalism and Concurrency Modeling}
The \emph{Temporal Logic of Actions (TLA+)}, introduced by Leslie Lamport~\cite{lamport2002specifying}, is a formal specification language based on first-order logic and set theory. It models concurrent and distributed systems as discrete state machines:
\begin{itemize}[itemsep=0.25em]
    \item \textbf{System Specification}: A system is defined by an initial state predicate $Init$, a next-state transition relation $Next$, and a canonical temporal formula $Spec \triangleq Init \land \Box[Next]_{vars} \land \text{Fairness}$.
    \item \textbf{Why We Use TLA+}:
    \begin{itemize}[itemsep=0.15em]
        \item \emph{Exact Concurrency Semantics}: Accurately captures non-deterministic thread interleavings, shared-memory synchronization (semaphores, locks), and race conditions without OS-level noise.
        \item \emph{Non-Invasive Instrumentation}: Allows auxiliary timing clocks ($t, T_{\text{start}}, t_{\text{prime}}$) and public trace variables to be added cleanly without altering functional program behavior.
        \item \emph{Automated Verification}: Replaces tedious, non-executable pen-and-paper Owicki--Gries proofs with automated, push-button verification.
    \end{itemize}
\end{itemize}

\subsection{PlusCal Algorithmic Language}
PlusCal is an imperative, C-style algorithmic language designed by Lamport~\cite{lamport2002specifying} that compiles directly into standard TLA+ specifications:
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Imperative Syntax}: Features familiar constructs (processes, loops, conditionals, and \texttt{await} guards) that map naturally to concurrent software. For practical model engineering, Wayne~\cite{wayne2018practical} establishes guidelines for structuring PlusCal processes, state variables, and execution invariants.
    \item \textbf{Label Granularity and Atomicity}: In PlusCal, every label defines the boundary of an atomic execution step. TLC only interleaves threads at label boundaries, giving us precise control over context switches and race conditions.
\end{itemize}

\subsection{The TLC Model Checker and Experimental Verification}
TLC is an explicit-state model checker that performs an exhaustive breadth-first traversal of the reachable state space from $Init$, checking for deadlocks and evaluating invariants at every state. In our experiments, TLC verifies information leaks and defenses using a dual-mode workflow:
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Mode A (Deductive Soundness)}: Verifies that the attacker's calibrated leaky assertions ($\text{Observed} \implies (A \iff h = \text{secret})$) hold across all reachable states. A result of zero violations proves the deduction is mathematically sound across all possible thread schedules.
    \item \textbf{Mode B (Leak Discovery)}: Checks the non-interference security invariant ($\text{NoTimingLeak}$). When a leak exists, TLC immediately halts and generates a minimal, step-by-step counterexample trace demonstrating the exact execution path and timing disparity that exposes the secret.
    \item \textbf{Mitigation Verification}: Checks the mitigated model (with candidate defenses like branch padding, dummy operations, or memory flushes), confirming 0 violations and verifying that the channel is closed.
\end{itemize}

\section{An Axiomatic Approach to Detect Information Leaks in Concurrent Programs}
Information flow security traditionally enforces \emph{Non-Interference (NI)}: confidential (high) inputs must not affect public (low) outputs. In concurrent systems, however, strict non-interference is overly restrictive.

\subsection{Limitations of Non-Interference in Concurrency}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{False Alarms from Scheduling}: In multi-threaded programs, thread scheduling, locks, and semaphores naturally cause non-deterministic timing jitter and interleavings. Static tools enforcing blanket non-interference reject safe code.
    \item \textbf{Targeted Leak Detection}: Rather than demanding total non-interference, Ghosal and Shyamasundar~\cite{ghosal2021axiomatic} proposed \emph{leaky assertions} to identify specific, exploitable leaks where public observations directly expose secret data.
\end{itemize}

\subsection{Definition and Mechanics of Leaky Assertions}
\begin{definition}[Leaky Assertion]
An assertion $A$ at a public observation point $\ell$ is \emph{leaky} if its satisfaction during execution reduces an observer's uncertainty about a confidential variable $h$.
\end{definition}
\noindent Formally, let $H$ be the set of possible secret values. An assertion $A$ is leaky if the subset of secret values consistent with observing $A$ is strictly smaller than $H$:
\begin{equation}
    H_{\text{deduced}} = \{ h \in H \mid \mathrm{Post}(\ell, h) \implies A \} \subsetneq H
\end{equation}
When $|H_{\text{deduced}}| = 1$, the observer uniquely reconstructs the exact secret value.

\subsection{Auxiliary Clocks and Timing Channels}
To observe side channels without altering functional behavior, the program is instrumented with auxiliary timing variables:
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Timing Instrumentation}: An entry timestamp $T_{\text{start}}$ records arrival, a clock $t$ advances with each step, and an exit timestamp $t_{\text{prime}}$ records completion at a public statement.
    \item \textbf{Timing Deductions}: When a secret branch causes lock contention or extra execution steps, elapsed time $\Delta = t_{\text{prime}} - T_{\text{start}}$ exposes the secret via calibrated assertions:
    \begin{align*}
        (\text{Observed} \land \Delta < \Delta_{\text{thresh}}) &\implies (h = 0) \\
        (\text{Observed} \land \Delta \ge \Delta_{\text{thresh}}) &\implies (h = 1)
    \end{align*}
    \item \textbf{From Paper Proofs to TLC}: While Ghosal and Shyamasundar verified these assertions only with manual pen-and-paper proofs, this thesis translates them into executable TLA+ models verified automatically across all interleavings using TLC.
\end{itemize}

\section{Concepts of Hoare Triples and Mathematical Foundations}
Hoare logic~\cite{hoare1969axiomatic} provides the formal mathematical foundation for reasoning about program correctness through assertions and pre-/postcondition contracts.

\subsection{The Hoare Triple and Notions of Correctness}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{The Hoare Triple ($\{P\}\, S \,\{Q\}$)}:
    \begin{itemize}[itemsep=0.15em]
        \item $P$ (\emph{Precondition}): An assertion over program variables that must hold before executing statement $S$.
        \item $S$ (\emph{Statement}): The program command or atomic action to be executed.
        \item $Q$ (\emph{Postcondition}): An assertion guaranteed to hold after $S$ executes, provided $S$ terminates.
    \end{itemize}
    \item \textbf{Partial vs.\ Total Correctness}:
    \begin{itemize}[itemsep=0.15em]
        \item \emph{Partial Correctness} ($\models_{\text{par}} \{P\}\, S \,\{Q\}$): Guarantees postcondition $Q$ if statement $S$ terminates (does not guarantee termination).
        \item \emph{Total Correctness} ($\models_{\text{tot}} \{P\}\, S \,\{Q\}$): Guarantees both that statement $S$ terminates and that the final state satisfies $Q$.
    \end{itemize}
    In side-channel verification, partial correctness formalizes state-invariance guarantees, while model checking verifies reachability and termination.
\end{itemize}

\subsection{Core Inference Rules}
Hoare logic provides compositional rules for deriving program properties step-by-step:
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Axiom of Assignment}: $\{P[e/x]\}\, x := e \,\{P\}$, replacing free occurrences of $x$ in $P$ with expression $e$.
    \item \textbf{Sequential Composition}: Chains consecutive statements by matching intermediate assertions ($\{P\}\, S_1 \,\{Q\}$ and $\{Q\}\, S_2 \,\{R\} \implies \{P\}\, S_1; S_2 \,\{R\}$).
    \item \textbf{Conditional Execution}: Analyzes branch paths under their respective path conditions ($\{P \land B\}\, S_1 \,\{Q\}$ and $\{P \land \neg B\}\, S_2 \,\{Q\}$).
    \item \textbf{Rule of Consequence}: Allows strengthening preconditions ($P \implies P'$) or weakening postconditions ($Q' \implies Q$).
    \item \textbf{Loop Invariant}: Identifies an assertion $I$ that remains invariant before, during, and after every loop iteration ($\{I \land B\}\, S \,\{I\}$).
\end{itemize}

\subsection{Weakest Preconditions and Verification Conditions}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Weakest Precondition ($\mathrm{wp}(S, Q)$)}: Defined by Dijkstra as the most general precondition that guarantees statement $S$ terminates in a state satisfying postcondition $Q$.
    \item \textbf{Verification Condition}: Checking whether a program satisfies contract $\{P\}\, S \,\{Q\}$ reduces to proving the first-order logical implication:
    \begin{equation}
        P \implies \mathrm{wp}(S, Q)
    \end{equation}
    This deductive principle underpins how assertion-based reasoning verifies program safety conditions.
\end{itemize}

\section{An Axiomatic Proof Technique for Parallel Programs}
Owicki and Gries~\cite{owicki1976axiomatic} extended Hoare logic to concurrent programs communicating through shared variables.

\subsection{Sequential Proof Outlines to Parallel Composition}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Sequential Proof Outlines}: Correctness of sequential code is established by inserting intermediate assertions at every statement boundary ($\{P_0\}\, S_1 \,\{P_1\} \dots S_m \,\{P_m\}$), where each step satisfies standard Hoare deduction rules.
    \item \textbf{Parallel Concurrency Failure}: In concurrent programs ($S = \textbf{cobegin } S_1 \parallel \dots \parallel S_n \textbf{ coend}$), proving individual threads in isolation is insufficient. Interleaved steps from peer threads can mutate shared memory and invalidate intermediate assertions.
\end{itemize}

\subsection{Interference Freedom and Auxiliary Variables}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Interference Freedom}: An assertion $P$ in thread $S_1$ is \emph{interference-free} with respect to an atomic action $T$ in thread $S_2$ if executing $T$ preserves $P$:
    \begin{equation}
        \{P \land \mathrm{pre}(T)\}\, T \,\{P\}
    \end{equation}
    When every statement in every thread is interference-free with all assertions of every other thread, the parallel composition is provably sound.
    \item \textbf{Auxiliary Variables}: Physical program variables alone are often insufficient to capture execution history or progress. Auxiliary variables:
    \begin{itemize}[itemsep=0.15em]
        \item Appear only in assignments $a := e$ and never appear in branch guards, loop tests, or expressions assigned to program variables.
        \item Record execution history, thread status, or timestamps without altering the program's functional state transitions.
    \end{itemize}
\end{itemize}

\subsection{Scalability Limitations of Manual Proofs}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Combinatorial Complexity}: For $n$ threads executing $m$ atomic statements, proving interference freedom requires evaluating $O(n^2 \cdot m^2)$ separate verification conditions by hand.
    \item \textbf{Need for Automated Model Checking}: When concurrent programs include loops, locks, and auxiliary clocks, manual proofs become tedious and error-prone. This scalability bottleneck motivates encoding models in TLA+ and using the TLC model checker for automated verification.
\end{itemize}

\section{Dynamic Labelling and Readers--Writers Flow Model (RWFM)}
Dynamic Labelling and the \emph{Readers--Writers Flow Model (RWFM)}~\cite{ghosal2018secrypt,ghosal2020dbsec} track information flow during execution without requiring rigid static security lattices:
\begin{itemize}[itemsep=0.3em]
    \item \textbf{Entity Labels}: Every entity $x$ (variable or channel) is assigned a label triple $(s_x, R_x, W_x)$, specifying its owner principal $s_x$, permitted readers $R_x$, and influencing writers $W_x$.
    \item \textbf{Permissible Flow Policy}: Information flows securely from entity $x$ to entity $y$ if and only if confidentiality ($R_x \supseteq R_y$) and integrity/provenance ($W_x \subseteq W_y$) are satisfied.
    \item \textbf{Dynamic Context Elevation}: When a thread enters a conditional branch guarded by a confidential variable $h$, the execution context elevates to confidential. Any shared synchronization primitive (such as a lock or semaphore) updated within that branch inherits the secret taint ($W_{\text{shared}} \leftarrow W_{\text{shared}} \cup \{\text{Secret}\}$).
    \item \textbf{Guiding Observation Point Selection}: When peer threads access secret-tainted synchronization primitives, resource contention creates observable timing delays or altered interleavings. Rather than implementing full dynamic lattice algebra, this thesis uses RWFM principles as a conceptual heuristic to identify candidate public observation points ($R = P$) for automated verification in TLA+/TLC.
\end{itemize}

\section{Open Challenges and Motivation}
Reviewing the literature reveals four core challenges in detecting information leaks in concurrent software:
\begin{itemize}[itemsep=0.3em]
    \item \textbf{Manual Proof Scalability}: Existing leaky assertion techniques~\cite{ghosal2021axiomatic} rely on pen-and-paper Owicki--Gries proofs, which quickly become intractable for systems with multiple threads, loops, and shared synchronization.
    \item \textbf{Lack of Generalizable Toolchains}: Prior investigations examined isolated scenarios but lacked a structured formal methodology, standardized invariant layering, or validation across diverse concurrency benchmarks.
    \item \textbf{Absence of Diagnostic Counterexamples}: Traditional static type systems report binary pass/fail outcomes without generating concrete execution traces that show developers exactly how a thread schedule exposes secret data.
    \item \textbf{Missing Integrated Mitigation Validation}: Existing approaches rarely verify candidate defenses (such as branch padding or memory barriers) within the same formal model used to identify the vulnerability.
\end{itemize}

\noindent \textbf{Research Motivation}: These limitations directly motivate our work: establishing an automated, explicit-state model checking framework in TLA+/TLC that translates axiomatic leaky assertions into executable specifications, extracts diagnostic counterexamples, and formally verifies that countermeasures eliminate side-channel leaks.

\chapter{METHODOLOGY}

\section{Verification Framework and Workflow}
The goal of our verification methodology is to provide an automated, executable technique to detect information leaks, prove the soundness of attacker deductions, and verify mitigations in concurrent programs. The framework translates high-level concurrent algorithms into executable formal specifications and uses the TLC model checker to exhaustively verify all possible thread schedules.

The end-to-end verification process consists of five interconnected phases:
\begin{enumerate}[label=\textbf{Phase \arabic*:}, leftmargin=1.9cm, itemsep=0.35em]
    \item \textbf{Preliminary Observation Point Selection}: As established in Section~2.5, we conceptually inspect the concurrent program using Readers--Writers Flow Model (RWFM) principles. By identifying statements where branches depend on secret inputs and mutate shared synchronization primitives, we select candidate entry points (e.g., $l_0: \texttt{print('c')}$) and exit points (e.g., $l_7: \texttt{print('d')}$) where side-channel leaks can manifest.
    \item \textbf{Algorithm Modeling in PlusCal}: We formalize the concurrent threads as PlusCal processes communicating via shared memory. Explicit statement labels are defined at every critical juncture to establish atomic execution boundaries.
    \item \textbf{Auxiliary Side-Channel Instrumentation}: We augment the specification with auxiliary clock variables ($t, T_{\text{start}}, t_{\text{prime}}$) and an output sequence ($\texttt{out}$) to measure timing differences and event orderings without perturbing program control flow.
    \item \textbf{Layered Invariant Formulation}: We specify three complementary invariant layers: functional correctness, calibration and leaky assertions (soundness of attacker deductions), and security non-interference properties.
    \item \textbf{Dual-Mode TLC Verification and Mitigation Checking}: We execute TLC across all reachable states:
    \begin{itemize}[itemsep=0.2em]
        \item \emph{Mode A (Soundness)}: Proves attacker deductions hold across all possible execution schedules (0 violations).
        \item \emph{Mode B (Leak Discovery)}: Refutes non-interference and extracts diagnostic counterexample traces demonstrating exactly how a schedule leaks data.
        \item \emph{Mitigation Verification}: Validates that candidate defenses (e.g., branch padding or memory fences) close the side channel with zero violations.
    \end{itemize}
\end{enumerate}

\section{PlusCal Algorithm Modeling and Label Granularity}
We author our formal models in PlusCal (C-syntax dialect), which compiles directly into standard TLA+ specifications.

\subsection{Process Structure and Shared State}
Concurrent programs are modeled as discrete processes operating over shared state:
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Process Declarations}: Each concurrent thread is declared as an independent process (e.g., \texttt{process T1 = 1} and \texttt{process T2 = 2}) with its own local state and program counter ($pc$).
    \item \textbf{Secret Initialization}: Secret variables are non-deterministically initialized across their possible value sets (e.g., $h \in \{0, 1\}$). TLC explores all possible secret assignments simultaneously in its initial state space.
    \item \textbf{Synchronization Primitives}: Shared locks, semaphores, and condition variables are modeled using \texttt{await} guards (e.g., \texttt{await sem > 0; sem := sem - 1;}) that block thread execution until the guard predicate is satisfied.
\end{itemize}

\subsection{Label Granularity and Interleaving Semantics}
In PlusCal, every label defines the exact boundary of an atomic execution step:
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Atomicity of Statements}: All code between two consecutive labels executes as a single, indivisible atomic transition.
    \item \textbf{Interleaving Control}: Context switches between concurrent threads can only occur at label boundaries. By placing labels at statement boundaries ($l_0, l_1, l_2, \dots$), we instruct TLC to evaluate every possible interleaving and race condition that could arise in a real preemptive multicore environment.
\end{itemize}

\section{Auxiliary Instrumentation for Side Channels}
To observe execution time and event ordering without altering functional program behavior, we instrument the PlusCal models with auxiliary variables.

\subsection{Non-Invasive Instrumentation Rules}
Following classical auxiliary variable principles (Owicki--Gries and Lamport), instrumented variables:
\begin{enumerate}[label=\arabic*., itemsep=0.2em]
    \item Appear strictly on the left-hand side of assignments ($v := e$).
    \item Never appear in branch conditions, loop guards, or expressions assigned to functional program variables.
\end{enumerate}
This ensures that the presence of auxiliary variables does not alter the reachable functional state transitions or thread scheduling of the system.

\subsection{Measurable Side-Channel Quantities}
We introduce four primary auxiliary instruments across our benchmarks:
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Global Virtual Clock ($t$)}: An integer variable initialized to $0$ that increments by $1$ tick with every atomic statement executed by any thread. This provides a non-invasive, discrete operational metric of execution duration.
    \item \textbf{Entry Timestamp ($T_{\text{start}}$)}: Recorded at the candidate entry observation point (e.g., $l_0: T_{\text{start}} := t$) when the observing process begins execution.
    \item \textbf{Exit Timestamp ($t_{\text{prime}}$)}: Recorded at the candidate exit observation point (e.g., $l_7: t_{\text{prime}} := t$) immediately before executing the public observable statement (such as \texttt{print('d')}).
    \item \textbf{Elapsed Duration ($\Delta$)}: Defined at the observation point as:
    \begin{equation}
        \Delta \triangleq t_{\text{prime}} - T_{\text{start}}
    \end{equation}
    where $\Delta$ captures the total time units elapsed between entry and exit, reflecting any synchronization delays or extra branch iterations caused by secret data.
    \item \textbf{Public Output Sequence ($\texttt{out}$)}: A sequence of strings initialized to $\langle \rangle$ that appends output tokens as threads execute print statements (e.g., $\texttt{out} := \text{Append}(\texttt{out}, \text{"c"})$), capturing the exact public observable event ordering.
\end{itemize}

\section{Layered Invariant Formulation}
To separate functional correctness from side-channel analysis, we structure our invariants into a three-layer hierarchy:

\subsection{Layer 1: Functional Correctness Invariants}
Before checking for information leaks, we verify that the program satisfies its intended functional specification:
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Type Safety (\texttt{TypeOK})}: Asserts that all variables remain within their declared mathematical domains (e.g., $\texttt{sem} \in \{0, 1\}$, $t \in \mathbb{N}$, $pc \in [\text{ProcSet} \to \text{Labels}]$).
    \item \textbf{Structural Invariants (\texttt{GlobalInv})}: Validates shared-memory safety contracts such as mutual exclusion:
    \begin{equation}
        \texttt{sem} + (\text{if } pc[1] \in \text{T1Crit} \text{ then } 1 \text{ else } 0) + (\text{if } pc[2] \in \text{T2Crit} \text{ then } 1 \text{ else } 0) = 1
    \end{equation}
    guaranteeing that at most one process can reside in its critical region at any time.
    \item \textbf{Functional Postcondition (\texttt{FunctionalPost})}: Encodes the functional contract, ensuring that upon termination, program variables compute the correct functional output (e.g., $v = 1 + 2h \land \texttt{sem} = 1$).
\end{itemize}

\subsection{Layer 2: Calibration and Leaky Assertions (Soundness)}
This layer formalizes the attacker's deductions based on public measurements:
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Calibration Bounds (\texttt{Calib0}, \texttt{Calib1})}: Establishes the exact reachability intervals of elapsed time $\Delta$ for each secret value under all possible thread schedules:
    \begin{align*}
        \texttt{Calib0} &\triangleq (\texttt{Observed} \land h = 0) \implies \Delta \in [\Delta_{\min}^{(0)}, \Delta_{\max}^{(0)}] \\
        \texttt{Calib1} &\triangleq (\texttt{Observed} \land h = 1) \implies \Delta \in [\Delta_{\min}^{(1)}, \Delta_{\max}^{(1)}]
    \end{align*}
    accounting for non-deterministic concurrency jitter introduced by peer threads.
    \item \textbf{Calibrated Leaky Assertions (\texttt{LA\_*})}: Expresses the mathematical implication from public observations to the secret:
    \begin{align*}
        \texttt{LA\_Low}   &\triangleq (\texttt{Observed} \land \Delta < \Delta_{\text{lo}}) \implies (h = 0) \\
        \texttt{LA\_High}  &\triangleq (\texttt{Observed} \land \Delta \ge \Delta_{\text{hi}}) \implies (h = 1) \\
        \texttt{LA\_Trace} &\triangleq \texttt{ACDB} \implies (h = 0)
    \end{align*}
\end{itemize}

\subsection{Layer 3: Security Invariants (Non-Interference)}
To test whether the program is vulnerable to information leaks, we specify non-interference security properties asserting that public observations are invariant to secret inputs:
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Timing Indistinguishability (\texttt{NoTimingLeak})}: Asserts that elapsed duration $\Delta$ falls strictly within the safe overlapping range where the attacker cannot distinguish $h = 0$ from $h = 1$:
    \begin{equation}
        \texttt{NoTimingLeak} \triangleq \texttt{Observed} \implies (\Delta \ge \Delta_{\text{lo}} \land \Delta < \Delta_{\text{hi}})
    \end{equation}
    \item \textbf{Order Indistinguishability (\texttt{NoOrderLeak})}: Asserts that leaking output order patterns (e.g., \texttt{ACDB}) are never produced:
    \begin{equation}
        \texttt{NoOrderLeak} \triangleq \neg \texttt{ACDB}
    \end{equation}
\end{itemize}

\section{TLC Model Checker Execution and Trace Interpretation}
The TLC model checker exhaustively traverses the state space to evaluate our specifications.

\subsection{Configuration and Execution Modes}
Each benchmark is paired with a formal configuration specifying constant thresholds ($\Delta_{\text{lo}}, \Delta_{\text{hi}}$), specification formula, and invariants to check. We execute TLC in two complementary verification modes:
\begin{itemize}[itemsep=0.35em]
    \item \textbf{Mode A (Soundness Verification)}: Checks Layer 1 functional invariants, calibration bounds, and leaky assertions (\texttt{TypeOK}, \texttt{GlobalInv}, \texttt{FunctionalPost}, \texttt{Calib*}, \texttt{LA\_*}). A \textbf{PASS (0 errors)} result proves that whenever the public observation occurs, the attacker's deduction holds across every possible thread schedule.
    \item \textbf{Mode B (Leak Discovery)}: Checks Layer 1 functional invariants alongside Layer 3 security invariants (\texttt{TypeOK}, \texttt{GlobalInv}, \texttt{NoTimingLeak}, \texttt{NoOrderLeak}). A \textbf{FAIL (Violation)} result refutes non-interference and prints a concrete counterexample trace witnessing how the leak occurs.
    \item \textbf{Mitigated Mode}: Evaluates the security invariants with proposed defenses enabled (\texttt{Fixed = TRUE}). A \textbf{PASS (0 errors)} result formally verifies that the mitigation eliminates the side channel across all schedules.
\end{itemize}

\subsection{Interpreting Diagnostic Counterexample Traces}
When a security invariant is violated in Mode B, TLC outputs the state space diameter, the total and distinct state counts, and the exact sequence of states leading to the violation.

For example, when checking the concurrent synchronization benchmark under Mode B, TLC explores 44 states (39 distinct states, diameter 5) and reports:
\begin{center}
    \texttt{Error: Invariant NoTimingLeak is violated.}
\end{center}
TLC then outputs a concrete 5-step diagnostic error trace:
\begin{enumerate}[label=\textbf{Step \arabic*:}, leftmargin=1.8cm, itemsep=0.3em]
    \item \textbf{Initial Predicate}: TLC initializes state variables ($h = 0, \texttt{sem} = 1, t = 0, T_{\text{start}} = 0, t_{\text{prime}} = 0, v = 0, \texttt{out} = \langle \rangle, pc = \langle \text{"T1\_1"}, \text{"l0"} \rangle$).
    \item \textbf{Entry Point ($l_0$)}: Process $T_2$ executes statement $l_0$, recording entry timestamp $T_{\text{start}} = 0$, advancing clock to $t = 1$, outputting $\texttt{"c"}$ ($\texttt{out} = \langle \text{"c"} \rangle$), and transitioning $pc[2]$ to \text{"l1"}.
    \item \textbf{Branch Decision ($l_1$)}: Process $T_2$ evaluates secret $h = 0$. Since $h \neq 1$, it bypasses semaphore acquisition and transitions $pc[2]$ directly to $l_6$ with $t = 1$.
    \item \textbf{Skip Operation ($l_6$)}: Process $T_2$ executes \texttt{skip}, advancing clock to $t = 2$ and transitioning $pc[2]$ to exit point $l_7$.
    \item \textbf{Exit Point ($l_7$)}: Process $T_2$ executes $l_7$, recording exit timestamp $t_{\text{prime}} = 2$, advancing clock to $t = 3$, appending $\texttt{"d"}$ ($\texttt{out} = \langle \text{"c"}, \text{"d"} \rangle$), and transitioning $pc[2]$ to \text{"Done"}.
\end{enumerate}
At Step 5, the observer computes the elapsed duration:
\begin{equation}
    \Delta = t_{\text{prime}} - T_{\text{start}} = 2 - 0 = 2
\end{equation}
Because the secret branch was bypassed ($h = 0$), $T_2$ completed in only 2 ticks, whereas taking the branch ($h = 1$) requires acquiring \texttt{sem} and takes at least 4 ticks ($\Delta \ge 4$). Since $\Delta = 2 < \Delta_{\text{lo}}$, \texttt{NoTimingLeak} fails, providing the developer with an actionable, step-by-step witness of the timing channel.

\subsection{Mitigation Verification Workflow}
Once an error trace is extracted, candidate defenses (such as branch padding or memory barriers) are added to the specification, conditioned on a boolean configuration parameter (\texttt{Fixed = TRUE}). Re-running TLC under Mode B verifies that:
\begin{enumerate}[label=\arabic*., itemsep=0.2em]
    \item The security invariant (\texttt{NoTimingLeak} or \texttt{NoOrderLeak}) passes with \textbf{0 errors}.
    \item The state space exploration confirms that execution metrics are equalized across all secret values, proving that the side channel has been eliminated.
\end{enumerate}

\section{Tools and Modeling Environment}
Our verification workflow uses PlusCal, TLA+, and TLC:
\begin{itemize}[itemsep=0.35em]
    \item \textbf{PlusCal}: We wrote all benchmark models in PlusCal using its C-syntax dialect, following the practical modeling patterns outlined by Wayne~\cite{wayne2018practical}. PlusCal provides familiar imperative constructs (threads, loops, conditionals, and \texttt{await}) that compile directly into TLA+. In PlusCal, every label defines an atomic step boundary, allowing us to specify exactly where threads can interleave.
    \item \textbf{Temporal Logic of Actions (TLA+)}: TLA+ represents state transitions mathematically using unprimed variables for the current state and primed variables for the next state. This provides unambiguous semantics for every action.
    \item \textbf{TLC Model Checker}: TLC is an explicit-state model checker that visits all reachable states breadth-first. It checks safety invariants on each visited state and prints the shortest counterexample trace when an invariant fails.
    \item \textbf{Environment}: We ran TLC on Java 11 under macOS. Each benchmark has its own configuration file specifying constants, initial states, and invariant properties. We authored models in VS Code using the TLA+ extension and ran batch checks via the TLC command line.
\end{itemize}

\section{Scope and Practical Limitations}
We note the following boundaries and assumptions in our evaluation:
\begin{enumerate}[label=\arabic*., itemsep=0.35em]
    \item \textbf{Manual Model Translation}: We manually translated the benchmark algorithms into PlusCal and selected observation points based on RWFM principles. Building an automated front-end parser to generate TLA+ directly from source code is an important next step.
    \item \textbf{Selective Information-Flow Concepts}: We used RWFM for practical point selection (tracking secret branches and shared variable writes) without implementing full multi-level lattice algebra.
    \item \textbf{Finite Bounded State Spaces}: Like all explicit-state checkers, TLC requires bounded parameters (e.g., single secret bits, fixed loops, and small numbers of threads). While this proves absence of leaks across all interleavings for the chosen bounds, it does not replace general inductive proofs for unbounded thread counts.
\end{enumerate}

\section{Benchmark 1: Concurrent Synchronization and Order Channels}

\subsection{Problem Context and Research Origin}
This benchmark investigates secret-dependent lock contention in multi-threaded programs, originating from the study by Ghosal and Shyamasundar~\cite{ghosal2021axiomatic}. Two concurrent threads $T_1$ and $T_2$ contend for a shared binary semaphore (\texttt{sem}) and mutate shared variable $v$. Thread $T_2$ conditionally accesses the critical section depending on a confidential secret $h \in \{0, 1\}$.

\subsection{Leakage Mechanism and Secret Variables}
The benchmark exhibits both timing and execution order side channels:
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Secret Variable}: $h \in \{0, 1\}$ (high confidentiality), governing whether $T_2$ enters the critical section.
    \item \textbf{Timing Side Channel}: When $h = 0$, $T_2$ bypasses the semaphore critical section and completes quickly ($\Delta = t_{\text{prime}} - T_{\text{start}} \le 3$). When $h = 1$, $T_2$ serializes behind $T_1$, waiting for the semaphore release and suffering an observable delay ($\Delta \ge 7$).
    \item \textbf{Output Order Channel}: Interleaving produces observable output traces in $\texttt{out}$. When $h = 1$, serialization forces the trace prefix $\langle \text{"a"}, \text{"c"}, \text{"d"}, \text{"b"} \rangle$, whereas when $h = 0$, $T_2$ can finish earlier, producing traces such as $\langle \text{"c"}, \text{"a"}, \text{"d"}, \text{"b"} \rangle$.
\end{itemize}

\subsection{Leaky Assertions Formulation}
Evaluated at the public exit statement $l_7$ (\texttt{Observed}):
\begin{align*}
    \text{LA\_Timing}    &\equiv \text{Observed} \implies ((\Delta \ge 7) \iff (h = 1)) \\
    \text{LA\_Time\_Low}  &\equiv (\text{Observed} \land \Delta \le 3) \implies (h = 0) \\
    \text{LA\_Time\_High} &\equiv (\text{Observed} \land \Delta \ge 7) \implies (h = 1) \\
    \text{LA\_Trace1}     &\equiv (\text{Observed} \land \texttt{out} = \langle \text{"a"}, \text{"c"}, \text{"d"}, \text{"b"} \rangle) \implies (h = 1)
\end{align*}
The non-interference security invariant checked to detect the leak is $\text{NoTimingLeak} \equiv \text{Observed} \implies (\Delta = 3)$.

\subsection{TLC Model Configuration}
The TLC configuration specifies the execution bounds and invariant checks:
\begin{itemize}[itemsep=0.2em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec}
    \item \textbf{Constants}: $\Delta_{\text{lo}} = 4$, $\Delta_{\text{hi}} = 8$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}, \texttt{GlobalInv}, \texttt{FunctionalPost}
    \item \textbf{Mode A (Soundness)}: \texttt{Calib0}, \texttt{Calib1}, \texttt{LA\_Low}, \texttt{LA\_High}, \texttt{LA\_Trace}
    \item \textbf{Mode B (Leak Discovery)}: \texttt{NoTimingLeak}
\end{itemize}

\section{Benchmark 2: Round-Robin Internal Timing Covert Channel}

\subsection{Problem Context and Research Origin}
This benchmark investigates internal timing channels governed by deterministic scheduling, originating from the foundational work by Russo and Sabelfeld~\cite{russo2006closing}. Secret-dependent branching in a multi-threaded system scheduled under round-robin time slicing shifts the interleaving turns between threads, altering the overall completion time of the program.

\subsection{Leakage Mechanism and Secret Variables}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Secret Variables}: $h \in \{0, 1\}$ (branch secret) and $h_2 \in \mathbb{N}$ (cryptographic accumulator).
    \item \textbf{Turn-Shift Timing Channel}: Thread $T_1$ contains an unbalanced branch: the $h = 1$ path requires 3 turns before assigning $l := 1$, whereas the $h = 0$ path requires only 2 turns. This turn shift alters when Thread $T_2$ executes, causing total execution time between \texttt{"START"} and \texttt{"END"} to vary:
    \begin{equation}
        \Delta = 8 \text{ clock cycles when } h = 0, \qquad \Delta = 9 \text{ clock cycles when } h = 1
    \end{equation}
    An observer measuring total elapsed cycles directly deduces secret $h$.
\end{itemize}

\subsection{Leaky Assertions Formulation}
Evaluated upon thread termination (\texttt{Observed}):
\begin{align*}
    \text{Calib0}      &\equiv (\text{Observed} \land h = 0) \implies (\Delta = 8) \\
    \text{Calib1}      &\equiv (\text{Observed} \land h = 1) \implies (\Delta = 9) \\
    \text{LA\_Timing}  &\equiv \text{Observed} \implies ((\Delta \ge 9) \iff (h = 1))
\end{align*}
The non-interference security invariant checked to detect the leak is $\text{NoTimingLeak} \equiv \text{Observed} \implies (\Delta = 8)$.

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.2em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec}
    \item \textbf{Constants}: $\Delta_{\text{lo}} = 8$, $\Delta_{\text{hi}} = 9$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}, \texttt{FunctionalPost}
    \item \textbf{Mode A (Soundness)}: \texttt{Calib0}, \texttt{Calib1}, \texttt{LA\_Timing}
    \item \textbf{Mode B (Leak Discovery)}: \texttt{NoTimingLeak}
\end{itemize}

\section{Benchmark 3: Branch-Padding Countermeasure and Constant-Time Execution}

\subsection{Problem Context and Research Origin}
This benchmark formalizes and verifies the branch-padding countermeasure proposed by Russo and Sabelfeld~\cite{russo2006closing} and extended by Mantel and Starostin~\cite{mantel2015timing}. The objective is to eliminate the internal timing covert channel identified in Benchmark~2 by equalizing branch step counts.

\subsection{Mitigation Mechanism and Balanced Control Flow}
In the vulnerable model, taking $h = 0$ consumed 2 scheduler turns while $h = 1$ consumed 3 turns. The transformed program introduces an auxiliary padding statement (\texttt{l4\_pad}) on the shorter branch path:
\begin{align*}
    \text{Thread } T_1 \text{ (Padded)} &: \quad \textbf{if } h = 1 \textbf{ then } [h_2 := 2 \cdot h_2 + l; \; \texttt{skip;}] \\
    &\quad\quad \textbf{else } [\texttt{skip; } \mathbf{skip; \; /* \; l4\_pad \; */}] \; l := 1; \; \texttt{print('1');}
\end{align*}
Inserting \texttt{l4\_pad} forces both execution paths to consume exactly 3 scheduler turns before reaching $l_5$. Consequently, the total execution time becomes invariant:
\begin{equation}
    \Delta = 9 \text{ clock cycles across both } h = 0 \text{ and } h = 1
\end{equation}

\subsection{Leaky Assertions and Mitigation Invariants}
\begin{align*}
    \text{ConstantTime} &\equiv \text{Observed} \implies (\Delta = 9) \\
    \text{NoTimingLeak} &\equiv \text{ConstantTime}
\end{align*}
The attacker's prior leaky assertion $\text{LA\_Timing} \equiv \text{Observed} \implies (\Delta \ge 9 \iff h = 1)$ is defeated (evaluates to \textbf{False} when $h = 0$ because $\Delta = 9$).

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.2em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec}
    \item \textbf{Constants}: $\Delta_{\text{lo}} = 8$, $\Delta_{\text{hi}} = 9$
    \item \textbf{Invariants Checked}: \texttt{TypeOK}, \texttt{FunctionalPost}, \texttt{ConstantTime}, \texttt{NoTimingLeak}
    \item \textbf{Outcome}: Evaluates to \textbf{PASS (0 errors)}, formally verifying that the timing channel is closed.
\end{itemize}

\section{Benchmark 4: Cryptographic Modular Exponentiation Side Channel}

\subsection{Problem Context and Research Origin}
This benchmark models algorithmic timing vulnerabilities in the square-and-multiply algorithm used for modular exponentiation ($y^K \pmod N$), foundational to RSA and Diffie--Hellman implementations. The vulnerability was first identified by Kocher~\cite{kocher1996timing} and framed axiomatically by Ghosal and Shyamasundar~\cite{ghosal2021axiomatic}.

\subsection{Leakage Mechanism and Secret Variables}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Secret Variable}: $K \in \text{Seq}(\{0, 1\})$ (cryptographic private key), $\text{HW}(K) \in 0..\text{BITS}$ (Hamming weight).
    \item \textbf{Timing Channel}: In each bit iteration, modular squaring is executed unconditionally. Modular multiplication is executed only when secret bit $K[i] = 1$. Total execution duration is:
    \begin{equation}
        \Delta = \text{Len}(K) \cdot \text{SqCost} + \text{HW}(K) \cdot \text{MulCost}
    \end{equation}
    An external observer measuring elapsed duration directly learns the private key's Hamming weight.
\end{itemize}

\subsection{Leaky Assertions Formulation}
\begin{align*}
    \text{LeakyAssertion} &\equiv \text{Observed} \implies (\Delta \ge \text{Threshold} \iff \text{HW}(K) \ge \text{SecretThreshold}) \\
    \text{ConstantTime}   &\equiv \text{Observed} \implies (\Delta = \text{ExpectedConstantTime})
\end{align*}

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.2em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec}
    \item \textbf{Constants}: $N = 15$, $Y_0 = 7$, $\text{BITS} = 4$, $\text{MulCost} = 3$, $\text{SqCost} = 2$, $\text{PrintCost} = 1$, $\text{Fixed} \in \{\text{FALSE}, \text{TRUE}\}$, $\text{Threshold} = 2$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}, \texttt{Correct}
    \item \textbf{Mode A (Soundness)}: \texttt{LeakyAssertion} (evaluates to \textbf{TRUE} under $\texttt{Fixed = FALSE}$)
    \item \textbf{Mode B (Leak Discovery)}: \texttt{ConstantTime} (refuted under $\texttt{Fixed = FALSE}$, confirmed under $\texttt{Fixed = TRUE}$)
\end{itemize}

\section{Benchmark 5: Web Authentication Latency Side Channel}

\subsection{Problem Context and Research Origin}
This benchmark models remote timing vulnerabilities in web authentication endpoints, based on the predictive timing mitigation framework of Askarov, Zhang, and Myers~\cite{askarov2010predictive}. The system handles user login by checking whether the username exists before executing cryptographic password verification.

\subsection{Leakage Mechanism and Secret Variables}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Secret Variables}:
    \begin{itemize}[itemsep=0.15em]
        \item $\texttt{valid\_user} \in \{\text{TRUE}, \text{FALSE}\}$: Account existence metadata.
        \item $\texttt{password\_match} \in \{\text{TRUE}, \text{FALSE}\}$: Password verification outcome.
    \end{itemize}
    \item \textbf{Timing Channel}: When a username does not exist ($\neg\texttt{valid\_user}$), the server immediately aborts after database lookup ($\Delta = \text{LookupCost} = 1$). When the username exists but the password fails, the server computes an expensive password hash ($\Delta = \text{LookupCost} + \text{HashCost} = 1 + 10 = 11$). Both paths emit the identical string \texttt{"error message"}, but the response latency exposes whether the account exists.
\end{itemize}

\subsection{Leaky Assertions Formulation}
Evaluated at the response point $l_{\text{exit}}$:
\begin{align*}
    \text{LA\_Time\_Low}  &\equiv (\neg\text{Fixed} \land \text{Observed} \land \text{out}_{\text{err}} \land \Delta \le 1) \implies (h = 0) \\
    \text{LA\_Time\_High} &\equiv (\neg\text{Fixed} \land \text{Observed} \land \text{out}_{\text{err}} \land \Delta \ge 11) \implies (h = 1) \\
    \text{LA\_Timing}     &\equiv (\neg\text{Fixed} \land \text{Observed} \land \text{out}_{\text{err}}) \implies ((\Delta \ge 5) \iff (h = 1))
\end{align*}
where $\text{out}_{\text{err}} \equiv (\text{result} = \text{"error message"})$. The security invariant is $\text{NoTimingLeak} \equiv (\text{Observed} \land \text{out}_{\text{err}}) \implies (\Delta = 11)$.

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.2em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec}
    \item \textbf{Constants}: $\text{LookupCost} = 1$, $\text{HashCost} = 10$, $\text{Threshold} = 5$, $\text{Fixed} \in \{\text{FALSE}, \text{TRUE}\}$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}, \texttt{FunctionalCorrect}
    \item \textbf{Mode A (Soundness)}: \texttt{Calib0}, \texttt{Calib1}, \texttt{LA\_Time\_Low}, \texttt{LA\_Time\_High}, \texttt{LA\_Timing}
    \item \textbf{Mode B (Leak Discovery)}: \texttt{NoTimingLeak}
\end{itemize}

\section{Benchmark 6: Persistent Memory Seqlock Under Power Failure}

\subsection{Problem Context and Research Origin}
This benchmark investigates information disclosure in non-volatile persistent memory (PM) architectures under power failure, based on the research by Graeme Smith~\cite{smith2026persistent}. The protocol models a Linux reader-writer seqlock managing confidential and public data records.

\subsection{Leakage Mechanism and Secret Variables}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Secret Variable}: $h \in \{0, 1\}$ ($h = 1$ is confidential high data; $h = 0$ is public low data).
    \item \textbf{Persistent State}: \texttt{pm\_x1} (data record), \texttt{pm\_x2} (classification flag), and \texttt{pm\_c} (sequence counter).
    \item \textbf{Crash-Reboot Leakage}: Stores to data, classification tag, and sequence counter commit asynchronously under weak persistency. If data ($x_1 := 1$) and counter ($c$) persist to PM while the security tag ($x_2 := 1$) lags in volatile cache during a crash, post-reboot persistent memory is inconsistent: $c$ is even (indicating quiescent state) and $x_2 = 0$ (marking data as low), yet $x_1 = 1$ (high secret). A post-reboot reader reads $x_2 = 0$, assumes low classification, and emits the high secret $1$ over the public channel.
\end{itemize}

\subsection{Leaky Assertions Formulation}
\begin{align*}
    \text{LA\_PersistentLeak} &\equiv (\neg\text{Fixed} \land \text{crashed} \land \text{ReaderDone} \land (\exists k : \text{out}[k] = 1)) \implies (h = 1) \\
    \text{NoInformationLeak}  &\equiv \forall k \in 1..\text{Len}(\text{out}) : (\text{out}[k] = 1) \implies (h = 0)
\end{align*}

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.2em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec}
    \item \textbf{Constants}: $\text{Fixed} \in \{\text{FALSE}, \text{TRUE}\}$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}
    \item \textbf{Mode A (Soundness)}: \texttt{LA\_PersistentLeak}
    \item \textbf{Mode B (Leak Discovery)}: \texttt{NoInformationLeak}
\end{itemize}

\chapter{CONCLUSION AND FUTURE WORK}

\section{Conclusion}
This thesis presented an executable formal verification methodology using TLA+ and the TLC model checker to analyze information flow and side-channel vulnerabilities in concurrent software. By formalizing leaky assertions into executable TLA+ invariants, we bridged the gap between pen-and-paper axiomatic proofs and automated, push-button verification.

Our evaluation across six representative benchmarks demonstrated the practical value of the three-layer invariant hierarchy and dual-mode TLC checking:
\begin{itemize}[itemsep=0.3em]
    \item \textbf{Soundness of Deductions (Mode A)}: Formally certified that whenever public observations (timing intervals or event sequences) occur, the attacker's deduction regarding the secret value holds across all possible thread interleavings with zero violations.
    \item \textbf{Actionable Leak Discovery (Mode B)}: Refuted non-interference security properties and automatically extracted concrete, step-by-step counterexample traces exposing the exact thread schedules and synchronization delays that leak confidential data.
    \item \textbf{Verification of Mitigations}: Verified that software countermeasures (such as branch padding, constant-time operations, and persistent-memory cache flushes) successfully eliminate side-channel vulnerabilities across all reachable execution paths.
\end{itemize}

\section{Future Work}
In this work, the extraction of observation points, the placement of atomic step labels, and the formulation of leaky assertions were carried out manually. The principal direction for future work is the \textbf{automation} of this verification and mitigation pipeline:

\begin{enumerate}[label=\arabic*., itemsep=0.35em]
    \item \textbf{Automated Translation from Source Code to PlusCal}:
    Developing a compiler front-end (e.g., using Clang/LLVM for C/C++ or Soot for Java) to automatically parse high-level concurrent code, map statements to PlusCal actions with accurate label atomicity, and inject non-invasive auxiliary timing clocks ($t, T_{\text{start}}, t_{\text{prime}}$) and observable traces.

    \item \textbf{Automated Synthesis of Leaky Assertions}:
    Employing static taint analysis and symbolic execution to automatically track information flows from annotated secret variables to shared synchronization primitives, identify vulnerable observation points, and synthesize calibration bounds and leaky assertions without manual intervention.

    \item \textbf{Counterexample-Guided Automated Repair}:
    Creating tools that automatically parse TLC's diagnostic error traces and synthesize targeted countermeasures, such as inserting cycle-balancing branch padding or injecting persistent-memory fence instructions directly into the source code.
\end{enumerate}
