    % Abstract content
    Enforcing \textbf{information flow security} in concurrent programs is difficult. Points of public observation (I/O operations, synchronisation and stalling for example) may be dependent upon secret information. Differences in execution time, and reordering of execution caused by dependence on secret information allows an adversary to discover secret information. Axiomatic approaches, such as \textbf{leaky assertions} using \textbf{Owicki-Gries} reasoning, allow mathematical proof of information leakage through a point of public observation. However, finding vulnerable points and proving information leakage manually in complex programs is tedious, error-prone and impractical.

    This thesis combines information flow techniques with operational model checking. We translate the axiomatic leaky assertion approach to temporal safety properties expressed in \textbf{TLA+ (Temporal Logic of Actions)\slash PlusCal}. By adding extra clocks to capture timing information, the explicit model checker \textbf{TLC} is used to exhaustively check all possible thread interleavings. This allows us to confirm whether security properties hold in a program, and if not, to produce concrete counter-example traces showing information leaks.

    We evaluate our approach across six different benchmarks: semaphore synchronisation in shared memory, round-robin scheduling, branch padding defences, modular exponentiation in cryptography, timing channels during web authentication, and sequence locks in persistent memory. For all benchmarks, all reachable interleavings were checked in less than 730~ms. If any information leakage was possible in a vulnerable system, TLC found safety violations, and generated detailed counter-example traces showing the interleaving orders that caused information leakage. Within mitigated programs, TLC confirmed that on no reachable paths was information leaked. This demonstrates an automatic approach to find timing channels within concurrent software and validate mitigation strategies.

    \noindent\textbf{Keywords:} Information Flow Security, Leaky Assertions, Owicki-Gries Reasoning, TLA+\slash PlusCal, TLC Model Checker.

\chapter{INTRODUCTION}

\section{Background}
Modern software relies on concurrent execution to maximize multicore performance. In multi-threaded programs, sequential threads share memory address spaces and coordinate through synchronization primitives like mutexes and semaphores.

However, non-deterministic scheduling complicates information flow security. Sequential threads interact with publicly observable operations---such as I/O statements (\texttt{print}), synchronization actions, and delays (\texttt{sleep}). When threads interleave, shared-resource contention and secret-dependent branches dynamically alter thread schedules. Consequently, confidential variables influence execution latency and event orderings. An attacker observing these public points can measure timing channel differences or monitor event reorderings to deduce confidential data, even when secrets are never directly output.

\section{Problem Statement}
In concurrent programs, information can be leaked through public program points. If the control flow to reach those points depends on secret data, measurable timing discrepancies can arise between different thread interleavings, revealing sensitive information.

Consider the example in Figure~\ref{fig:motivating-example}. Two threads ($T_1, T_2$) compete for access to a common binary semaphore \texttt{sem} (initial value: 1) and modify a common variable ($v$, initial value: 0). Depending on the value of a secret bit $h \in \{0, 1\}$, thread $T_2$ may or may not execute its critical section between the public print statements \texttt{print('c')} and \texttt{print('d')}. If $h = 0$ then $T_2$ will not enter its critical section and will therefore quickly terminate (taking at most $\Delta = 3$ steps). However, if $h = 1$ then $T_2$ must wait behind $T_1$ and therefore experiences contention (taking $\ge 7$ steps). From measuring the runtime or output order, an attacker can infer the value of $h$.

Although information leaks at public program points can be formally proved insecure using an axiomatic approach (\emph{leaky assertions}), current techniques require manual proofs. Locating vulnerability points, finding appropriate invariants and proving that all thread interleavings do not leak information is very time consuming, error prone and not scalable. Manual proofs cannot automatically explore the concurrent program state space. They cannot also produce concrete counterexample executions of leaking schedules or verify mitigation solutions.

In this thesis we solve this problem. We translate leaky assertions to temporal safety properties in TLA+/PlusCal and allow the explicit model checker TLC to automatically detect timing leaks. Counterexample executions can be produced, and mitigation solutions can be verified to be secure for all reachable thread interleavings.

\section{Research Scope and Objectives}
This thesis links deductive information flow analysis to explicit-state model checking in order to find and confirm mitigations to side-channel leaks in systems. This thesis has four concrete aims:
\begin{enumerate}[label=\arabic*., itemsep=0.25em, topsep=0.2em]
    \item \textbf{Semantic Properties}: Prove the semantic link between Owicki--Gries interference-freedom, auxiliary clocks, and leaky assertions. Demonstrate interference-freedom ensures attacker deductions are preserved under all feasible execution paths (Proposition~3.1).
    \item \textbf{Identification}: Using dynamic labelling and the Readers--Writers Flow Model (RWFM), determine the public observation points which may be influenced by secret branches in the program and state modifications.
    \item \textbf{Multi-Layer Invariants and Verification}: Create a multi-layer invariant structure (functional correctness, calibration/leaky invariants, non-interference properties) to provide two forms of verification in TLC. Interleaving-agnostic verification can be performed (Mode~A) to prove deductive soundness, and diagnostic counterexample traces can be found (Mode~B).
    \item \textbf{Application and Mitigation Verification}: Six benchmark examples have been created, including concurrent synchronization, internal timing channels, algorithmic side channels, web services, and crash-consistent persistent memory. Within these examples, mitigations were proposed and verified to ensure they remove the covert channels.
\end{enumerate}
Within this work, observations, assertions, and models were manually created to provide rigorous proof of the key concepts and verification within this work. This creates a proven base from which tools can be developed in the future.

\chapter{LITERATURE REVIEW AND PRELIMINARIES}

\section{Temporal Logic of Actions (TLA+) by Leslie Lamport}

\subsection{TLA+ Formalism and Concurrency Modeling}
Temporal Logic of Actions (TLA+)~\cite{lamport2002specifying} uses set theory and first-order logic to specify concurrent and distributed systems. A system is specified via:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Initial State Predicate}: $Init$, defining valid starting states.
    \item \textbf{Next-State Relation}: $Next$, specifying permitted state transitions.
    \item \textbf{Temporal Property}: Canonical formula $Spec \triangleq Init \land \Box[Next]_{vars} \land \text{Fairness}$.
\end{itemize}
TLA+ provides three key modeling capabilities for our verification workflow:
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Precise Concurrency Semantics}: Accurately captures concurrency \\ (non-deterministic thread execution, semaphores/locks, and race conditions) without interference from operating system noise.
    \item \textbf{Non-Intrusive Timing Instrumentation}: Additional timing clocks ($t, T_{\text{start}}, t_{\text{prime}}$) and observable variables can be added without affecting the functionality of the program.
    \item \textbf{Automatic Verification}: Replaces complex manual proofs (Owicki--Gries proofs) with push-button automatic verification.
\end{itemize}

\subsection{PlusCal Algorithmic Language}
PlusCal is an imperative algorithmic specification language that can be compiled directly into standard TLA+. The language contains familiar imperative language features (processes, loops, branching, and \texttt{await} statements) to help specify concurrent software. To produce effective models, guidelines are provided by Wayne~\cite{wayne2018practical} for structuring PlusCal processes, state variables, and invariant properties. Each line (or label) in PlusCal corresponds to an atomic step in execution. As such, during verification with TLC, two processes can only be interleaved at line boundaries. This gives fine control over when context switches occur and how race conditions arise.

\subsection{The TLC Model Checker and Experimental Verification}
TLC is an explicit-state model checker. It performs a breadth-first search on all reachable states from the initial state ($Init$). Deadlock and invariant properties are analysed throughout the state space. Within this project, information leakage and mitigations have been verified in two modes within TLC:
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{In Mode A}: Verifies the attacker's calibrated leaking property ($\text{Observed} \implies (A \iff h = \text{secret})$) across all reachable states. If no violations occur, it has been proved mathematically valid in all possible thread executions.
    \item \textbf{In Mode B}: The security property \texttt{NoTimingLeak} is checked. If there is information leakage, model checking will stop immediately and a shortest counterexample will be produced to show the path through the model and the timing difference in the execution path that causes the secret to be leaked.
    \item \textbf{Mitigated Model}: Finally, in the mitigated model (with potential mitigations, such as branch padding, dummy operations, or memory flushing), verification confirms that 0 violations occur and that the channel has been closed.
\end{itemize}

\section{An Axiomatic Approach to Detect Information Leaks in Concurrent Programs}
Security in information flow ensures non-interference, so that secrets (high) do not influence public outputs (low). However, in concurrent programs, requiring strict non-interference can be too restrictive.

\subsection{Limitations of Non-Interference in Concurrency}
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Too Many False Positives}: Multi-threading can lead to non-deterministic timing variations using locking mechanisms and semaphores. Tools enforcing non-interference may produce many false negatives.
    \item \textbf{Leaky Assertions}: Instead of enforcing strict non-interference, Ghosal and Shyamasundar~\cite{ghosal2021axiomatic} introduce the concept of leaky assertions, which allow the identification of targeted leaks in a program. Here, public observations directly reveal secrets.
\end{itemize}

\subsection{Definition and Mechanics of Leaky Assertions}
\begin{definition}[Leaky Assertion]
A Leaky Assertion occurs at public observation location $\ell$. Observation of assertion $A$ reduces uncertainty in the value of secret variable $h$. Given a set $H$ of possible secret values, an assertion $A$ is leaky when the set of secret values consistent with the observation of assertion $A$ is a proper subset of $H$ (the deduction of secret values):
\begin{equation}
    H_{\text{deduced}} = \{ h \in H \mid \mathrm{Post}(\ell, h) \implies A \} \subsetneq H
\end{equation}
If $|H_{\text{deduced}}| = 1$ then it is possible to exactly deduce the value of the secret.
\end{definition}

\subsection{Auxiliary Clocks and Timing Channels}
Timing variables are added to allow side-channel analysis without changing program functionality:
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Timing Analysis}: A start time ($T_{\text{start}}$) is recorded when entering the program. A timing variable ($t$) increments with every step in the program. A finish time ($t_{\text{prime}}$) is recorded when exiting the program at a public statement.
    \item \textbf{Deduction}: If the secret is taken to be true, causing contentions in locks or increasing the number of operations, the time it takes to execute $\Delta = t_{\text{prime}} - T_{\text{start}}$ can be used to detect the secret. If $\Delta < \Delta_{\text{thresh}}$ then $(\text{Observed} \land \Delta < \Delta_{\text{thresh}}) \implies (h = 0)$. If $\Delta \ge \Delta_{\text{thresh}}$ then $(\text{Observed} \land \Delta \ge \Delta_{\text{thresh}}) \implies (h = 1)$.
    \item \textbf{Automatic Verification}: In~\cite{ghosal2021axiomatic}, these assertions were only manually proven. This thesis has been implemented as an automatic TLA+ model, and verified for all interleavings using the TLC tool.
\end{itemize}

\section{Concepts of Hoare Triples and Mathematical Foundations}
Hoare logic~\cite{hoare1969axiomatic} provides the formal mathematical foundation for reasoning about program correctness through assertions and pre-/postcondition contracts.

\subsection{The Hoare Triple and Notions of Correctness}
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{The Hoare Triple ($\{P\}\, S \,\{Q\}$)}:
    \begin{itemize}[itemsep=0.15em]
        \item $P$ (\emph{Precondition}): An assertion over program variables that must hold before executing statement $S$.
        \item $S$ (\emph{Statement}): The program command or atomic action to be executed.
        \item $Q$ (\emph{Postcondition}): A postcondition guaranteed to hold at the end of $S$ assuming termination.
    \end{itemize}
    \item \textbf{Partial and Total Correctness}:
    \begin{itemize}[itemsep=0.15em]
        \item \emph{Partial Correctness} ($\models_{\text{par}} \{P\}\, S \,\{Q\}$): Guarantees that the postcondition $Q$ holds once execution has finished. It does not guarantee that execution will finish.
        \item \emph{Total Correctness} ($\models_{\text{tot}} \{P\}\, S \,\{Q\}$): Guarantees that execution will finish and at the end of execution $Q$ is true in the new state.
    \end{itemize}
    Partial correctness ensures that the state is invariant under program execution within side channels. Model checking ensures reachability and termination.
\end{itemize}

\subsection{Core Inference Rules}
Hoare logic provides compositional rules for deriving program properties step-by-step:
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Axiom of Assignment}: $\{P[e/x]\}\, x := e \,\{P\}$, replacing free occurrences of $x$ in $P$ with expression $e$.
    \item \textbf{Sequential Composition}: Chains consecutive statements by matching intermediate assertions ($\{P\}\, S_1 \,\{Q\}$ and $\{Q\}\, S_2 \,\{R\} \implies \{P\}\, S_1; S_2 \,\{R\}$).
    \item \textbf{Conditional Execution}: Analyzes branch paths under their respective path conditions ($\{P \land B\}\, S_1 \,\{Q\}$ and $\{P \land \neg B\}\, S_2 \,\{Q\}$).
    \item \textbf{Rule of Consequence}: Allows strengthening preconditions ($P \implies P'$) or weakening postconditions ($Q' \implies Q$).
    \item \textbf{Loop Invariance}: A condition $I$ that is true before, during, and after execution of each loop iteration ($\{I \land B\}\, S \,\{I\}$).
\end{itemize}

\subsection{Weakest Preconditions and Verification Conditions}
\begin{itemize}[itemsep=0.25em, topsep=0.15em]
    \item \textbf{Weakest Precondition ($\mathrm{wp}(S, Q)$)}: The strongest precondition that guarantees termination and that the postcondition $Q$ holds after execution of $S$.
    \item \textbf{Verification Conditions}: To verify that a program satisfies contract $\{P\}\, S \,\{Q\}$, it must be possible to prove that:
    \begin{equation}
        P \implies \mathrm{wp}(S, Q)
    \end{equation}
    This principle allows assertions to be used to verify safety conditions in programs.
\end{itemize}

\section{An Axiomatic Proof Technique for Parallel Programs}
Owicki and Gries~\cite{owicki1976axiomatic} extended Hoare logic to concurrent programs communicating through shared variables.

\subsection{Sequential Proof Outlines to Parallel Composition}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Sequential Proof Outlines}: Correctness of sequential code is established by inserting intermediate assertions at statement boundaries ($\{P_0\}\, S_1 \,\{P_1\} \dots S_m \,\{P_m\}$), where each step satisfies standard Hoare deduction rules.
    \item \textbf{Parallel Concurrency Failure}: In concurrent programs ($S = \textbf{cobegin } S_1 \parallel \dots \parallel S_n \textbf{ coend}$), proving individual threads in isolation is insufficient. Interleaved steps from peer threads can mutate shared memory and invalidate intermediate assertions.
\end{itemize}

\subsection{Interference Freedom and Auxiliary Variables}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Interference Freedom}: An assertion $P$ in thread $S_1$ is \emph{interference-free} with respect to an atomic action $T$ in thread $S_2$ if executing $T$ preserves $P$:
    \begin{equation}
        \{P \land \mathrm{pre}(T)\}\, T \,\{P\}
    \end{equation}
    When every statement in every thread is interference-free with all assertions of every other thread, the parallel composition is provably sound.
    \item \textbf{Auxiliary Variables}: Physical program variables alone are often insufficient to capture execution history or progress. Auxiliary variables:
    \begin{itemize}[itemsep=0.15em]
        \item Appear only in assignments $a := e$ and never appear in branch guards, loop tests, or expressions assigned to program variables.
        \item Record execution history, thread status, or timestamps without altering the program's functional state transitions.
    \end{itemize}
\end{itemize}

\subsection{Scalability Limitations of Manual Proofs}
\begin{itemize}[itemsep=0.25em]
    \item \textbf{Combinatorial Complexity}: For $n$ threads executing $m$ atomic statements, proving interference freedom requires evaluating $O(n^2 \cdot m^2)$ separate verification conditions by hand.
    \item \textbf{Need for Automated Model Checking}: When concurrent programs include loops, locks, and auxiliary clocks, manual proofs become tedious and error-prone. This scalability bottleneck motivates encoding models in TLA+ and using the TLC model checker for automated verification.
\end{itemize}

\section{Dynamic Labelling and Readers--Writers Flow Model (RWFM)}
Dynamic Labelling and the \emph{Readers--Writers Flow Model (RWFM)}~\cite{ghosal2018secrypt,ghosal2020dbsec} track information flow during execution without requiring rigid static security lattices:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Entity Labels}: Every entity $x$ is assigned a label triple $(s_x, R_x, W_x)$, specifying owner $s_x$, readers $R_x$, and writers $W_x$.
    \item \textbf{Permissible Flow Policy}: Information flows securely from $x$ to $y$ iff confidentiality ($R_x \supseteq R_y$) and integrity ($W_x \subseteq W_y$) hold.
    \item \textbf{Dynamic Context Elevation}: When branching on secret $h$, execution context elevates ($\lambda(pc) = \top$). Shared synchronization primitives mutated within the branch inherit the secret taint ($W_{\text{shared}} \leftarrow W_{\text{shared}} \cup \{\text{Secret}\}$).
    \item \textbf{Guiding Observation Point Selection}: Contention over secret-tainted primitives creates observable timing delays. We use RWFM principles to identify candidate public observation points ($R = P$) for automated verification in TLA+/TLC.
\end{itemize}

\subsection{Statement Classification and Observation Point Identification}
To identify which public statements in a concurrent program are vulnerable to covert timing or order leaks, we inspect the program's control flow and shared-state interactions. Specifically, we classify each statement based on its operational role, whether it executes in a confidential context (following a branch on secret data), and whether it mutates shared synchronization primitives:
\begin{itemize}[itemsep=0.2em, topsep=0.15em]
    \item \textbf{Process $T_1$ (Public Peer)}: Consists of public synchronization guards ($l_0: \texttt{await } sem > 0$), semaphore decrements and increments ($l_1, l_5$), observable outputs ($l_2: \texttt{print('a')}, l_4: \texttt{print('b')}$), and non-secret variable updates ($l_3: v = v + 1$). None of $T_1$'s operations depend directly on confidential data.
    \item \textbf{Process $T_2$ (Secret-Dependent Thread)}: Commences at public statement $l_0: \texttt{print('c')}$, which establishes entry observation point $T_{\text{start}}$. At statement $l_1: \texttt{if } h \texttt{ then}$, control splits conditionally based on secret variable $h$.
    \item \textbf{Branch-Dependent Execution Paths}: When $h = 1$, $T_2$ contends with $T_1$ for shared semaphore \texttt{sem} ($l_2, l_3$), updates $v$ ($l_4$), and releases \texttt{sem} ($l_5$), incurring lock-contention latency. When $h = 0$, $T_2$ bypasses the critical section via $l_6: \texttt{skip}$, terminating quickly.
    \item \textbf{Candidate Leaking Exit Point}: Both paths converge at public statement $l_7: \texttt{print('d')}$. Because $l_7$ immediately succeeds this secret-dependent divergence in execution duration, it constitutes a prime observation point ($t_{\text{prime}}$) where an attacker can observe timing and order differences.
\end{itemize}
Consequently, our methodology designates $l_0$ as the candidate entry observation point and $l_7$ as the candidate exit observation point for automated model checking in TLA+\slash TLC.

\chapter{METHODOLOGY}

\section{Verification Framework and Workflow}
The goal of our verification methodology is to provide an automated, executable technique to detect information leaks, prove the soundness of attacker deductions, and verify mitigations in concurrent programs. The framework translates high-level concurrent algorithms into executable formal specifications and uses the TLC model checker to exhaustively verify all possible thread schedules.

The end-to-end verification process consists of five interconnected phases:
\begin{enumerate}[label=\textbf{Phase \arabic*:}, leftmargin=1.9cm, itemsep=0.15em, topsep=0.15em]
    \item \textbf{Preliminary Observation Point Selection}: As established in Section~2.5, we conceptually inspect the concurrent program using Readers--Writers Flow Model (RWFM) principles. By identifying statements where branches depend on secret inputs and mutate shared synchronization primitives, we select candidate entry points (e.g., $l_0: \texttt{print('c')}$) and exit points (e.g., $l_7: \texttt{print('d')}$) where side-channel leaks can manifest.
    \item \textbf{Algorithm Modeling in PlusCal}: We formalize the concurrent threads as PlusCal processes communicating via shared memory. Explicit statement labels are defined at every critical juncture to establish atomic execution boundaries.
    \item \textbf{Auxiliary Side-Channel Instrumentation}: We augment the specification with auxiliary clock variables ($t, T_{\text{start}}, t_{\text{prime}}$) and an output sequence ($\texttt{out}$) to measure timing differences and event orderings without perturbing program control flow.
    \item \textbf{Layered Invariant Formulation}: We specify three complementary invariant layers: functional correctness, calibration and leaky assertions (soundness of attacker deductions), and security non-interference properties.
    \item \textbf{Dual-Mode TLC Verification and Mitigation Checking}: We execute TLC across all reachable states:
    \begin{itemize}[itemsep=0.1em, topsep=0.1em]
        \item \emph{Mode A (Soundness)}: Proves attacker deductions hold across all possible execution schedules (0 violations).
        \item \emph{Mode B (Leak Discovery)}: Refutes non-interference and extracts diagnostic counterexample traces demonstrating exactly how a schedule leaks data.
        \item \emph{Mitigation Verification}: Validates that candidate defenses (e.g., branch padding or memory fences) close the side channel with zero violations.
    \end{itemize}
\end{enumerate}

\section{PlusCal Algorithm Modeling and Label Granularity}
We author our formal models in PlusCal (C-syntax dialect), which compiles directly into standard TLA+ specifications.

\subsection{Process Structure and Shared State}
The concurrent thread structure evaluated across our core benchmarks (introduced in Figure~\ref{fig:motivating-example}) comprises concurrent processes synchronizing via shared state and conditional on secret data. In our methodology, concurrent programs are modeled as discrete PlusCal processes operating over shared state:
\begin{itemize}[itemsep=0.15em, topsep=0.15em]
    \item \textbf{Process Declarations}: Each concurrent thread is declared as an independent process (e.g., \texttt{process T1 = 1} and \texttt{process T2 = 2}) with its own local state and program counter ($pc$).
    \item \textbf{Secret Initialization}: Secret variables are non-deterministically initialized across their possible value sets (e.g., $h \in \{0, 1\}$). TLC explores all possible secret assignments simultaneously in its initial state space.
    \item \textbf{Synchronization Primitives}: Shared locks, semaphores, and condition variables are modeled using \texttt{await} guards (e.g., \texttt{await sem > 0; sem := sem - 1;}) that block thread execution until the guard predicate is satisfied.
\end{itemize}

\subsection{Label Granularity and Interleaving Semantics}
In PlusCal, every label defines the exact boundary of an atomic execution step:
\begin{itemize}[itemsep=0.15em, topsep=0.15em]
    \item \textbf{Atomicity of Statements}: All code between two consecutive labels executes as a single, indivisible atomic transition.
    \item \textbf{Interleaving Control}: Context switches between concurrent threads can only occur at label boundaries. By placing labels at statement boundaries ($l_0, l_1, l_2, \dots$), we instruct TLC to evaluate every possible interleaving and race condition that could arise in a real preemptive multicore environment.
\end{itemize}

\section{Auxiliary Instrumentation for Side Channels}
To observe execution time and event ordering without altering functional program behavior, we instrument the PlusCal models with auxiliary variables.

\subsection{Non-Invasive Instrumentation Rules}
Following classical auxiliary variable principles (Owicki--Gries and Lamport), instrumented variables:
\begin{enumerate}[label=\arabic*., itemsep=0.15em, topsep=0.15em]
    \item Appear strictly on the left-hand side of assignments ($v := e$).
    \item Never appear in branch conditions, loop guards, or expressions assigned to functional program variables.
\end{enumerate}
This ensures that the presence of auxiliary variables does not alter the reachable functional state transitions or thread scheduling of the system.

\subsection{Measurable Side-Channel Quantities}
We introduce four primary auxiliary instruments across our benchmarks:
\begin{itemize}[itemsep=0.15em, topsep=0.15em]
    \item \textbf{Global Virtual Clock ($t$)}: An integer variable initialized to $0$ that increments by $1$ tick with every atomic statement executed by any thread. This provides a non-invasive, discrete operational metric of execution duration.
    \item \textbf{Entry Timestamp ($T_{\text{start}}$)}: Recorded at the candidate entry observation point (e.g., $l_0: T_{\text{start}} := t$) when the observing process begins execution.
    \item \textbf{Exit Timestamp ($t_{\text{prime}}$)}: Recorded at the candidate exit observation point (e.g., $l_7: t_{\text{prime}} := t$) immediately before executing the public observable statement (such as \texttt{print('d')}).
    \item \textbf{Elapsed Duration ($\Delta$)}: Defined at the observation point as:
    \begin{equation}
        \Delta \triangleq t_{\text{prime}} - T_{\text{start}}
    \end{equation}
    where $\Delta$ captures the total time units elapsed between entry and exit, reflecting any synchronization delays or extra branch iterations caused by secret data.
    \item \textbf{Public Output Sequence ($\texttt{out}$)}: A sequence of strings initialized to $\langle \rangle$ that appends output tokens as threads execute print statements (e.g., $\texttt{out} := \text{Append}(\texttt{out}, \text{"c"})$), capturing the exact public observable event ordering.
\end{itemize}

\section{Layered Invariant Formulation}
To separate functional correctness from side-channel analysis, we structure our invariants into a three-layer hierarchy:

\subsection{Layer 1: Functional Correctness Invariants}
Before checking for information leaks, we verify that the program satisfies its intended functional specification:
\begin{itemize}[itemsep=0.15em, topsep=0.15em]
    \item \textbf{Type Safety (\texttt{TypeOK})}: Asserts that all variables remain within their declared mathematical domains (e.g., $\texttt{sem} \in \{0, 1\}$, $t \in \mathbb{N}$, $pc \in [\text{ProcSet} \to \text{Labels}]$).
    \item \textbf{Structural Invariants (\texttt{GlobalInv})}: Validates shared-memory safety contracts such as mutual exclusion:
    \begin{equation}
        \texttt{sem} + (\text{if } pc[1] \in \text{T1Crit} \text{ then } 1 \text{ else } 0) + (\text{if } pc[2] \in \text{T2Crit} \text{ then } 1 \text{ else } 0) = 1
    \end{equation}
    guaranteeing that at most one process can reside in its critical region at any time.
    \item \textbf{Functional Postcondition (\texttt{FunctionalPost})}: Encodes the functional contract, ensuring that upon termination, program variables compute the correct functional output (e.g., $v = 1 + 2h \land \texttt{sem} = 1$).
\end{itemize}

\subsection{Layer 2: Calibration and Leaky Assertions (Soundness)}
This layer formalizes the attacker's deductions based on public measurements:
\begin{itemize}[itemsep=0.15em, topsep=0.15em]
    \item \textbf{Calibration Bounds (\texttt{Calib0}, \texttt{Calib1})}: Establishes the exact reachability intervals of elapsed time $\Delta$ for each secret value under all possible thread schedules:
    \begin{align*}
        \texttt{Calib0} &\triangleq (\texttt{Observed} \land h = 0) \implies \Delta \in [\Delta_{\min}^{(0)}, \Delta_{\max}^{(0)}] \\
        \texttt{Calib1} &\triangleq (\texttt{Observed} \land h = 1) \implies \Delta \in [\Delta_{\min}^{(1)}, \Delta_{\max}^{(1)}]
    \end{align*}
    accounting for non-deterministic concurrency jitter introduced by peer threads.
    \item \textbf{Calibrated Leaky Assertions (\texttt{LA\_*})}: Expresses the mathematical implication from public observations to the secret:
    \begin{align*}
        \texttt{LA\_Low}   &\triangleq (\texttt{Observed} \land \Delta < \Delta_{\text{lo}}) \implies (h = 0) \\
        \texttt{LA\_High}  &\triangleq (\texttt{Observed} \land \Delta \ge \Delta_{\text{hi}}) \implies (h = 1) \\
        \texttt{LA\_Trace} &\triangleq \texttt{ACDB} \implies (h = 0)
    \end{align*}
\end{itemize}

\subsection{Layer 3: Security Invariants (Non-Interference)}
To test whether the program is vulnerable to information leaks, we specify non-interference security properties asserting that public observations are invariant to secret inputs:
\begin{itemize}[itemsep=0.15em, topsep=0.15em]
    \item \textbf{Timing Indistinguishability (\texttt{NoTimingLeak})}: Asserts that elapsed duration $\Delta$ falls strictly within the safe overlapping range where the attacker cannot distinguish $h = 0$ from $h = 1$:
    \begin{equation}
        \texttt{NoTimingLeak} \triangleq \texttt{Observed} \implies (\Delta \ge \Delta_{\text{lo}} \land \Delta < \Delta_{\text{hi}})
    \end{equation}
    \item \textbf{Order Indistinguishability (\texttt{NoOrderLeak})}: Asserts that leaking output order patterns (e.g., \texttt{ACDB}) are never produced:
    \begin{equation}
        \texttt{NoOrderLeak} \triangleq \neg \texttt{ACDB}
    \end{equation}
\end{itemize}

\section{TLC Model Checker Execution and Trace Interpretation}
The TLC model checker exhaustively traverses the state space to evaluate our specifications.

\subsection{Configuration and Execution Modes}
Each benchmark is paired with a formal configuration specifying constant thresholds ($\Delta_{\text{lo}}, \Delta_{\text{hi}}$), specification formula, and invariants to check. We execute TLC in two complementary verification modes:
\begin{itemize}[itemsep=0.15em, topsep=0.15em]
    \item \textbf{Mode A (Soundness Verification)}: Checks Layer 1 functional invariants, calibration bounds, and leaky assertions (\texttt{TypeOK}, \texttt{GlobalInv}, \texttt{FunctionalPost}, \texttt{Calib*}, \texttt{LA\_*}). A \textbf{PASS (0 errors)} result proves that whenever the public observation occurs, the attacker's deduction holds across every possible thread schedule.
    \item \textbf{Mode B (Leak Discovery)}: Checks Layer 1 functional invariants alongside Layer 3 security invariants (\texttt{TypeOK}, \texttt{GlobalInv}, \texttt{NoTimingLeak}, \texttt{NoOrderLeak}). A \textbf{FAIL (Violation)} result refutes non-interference and prints a concrete counterexample trace witnessing how the leak occurs.
    \item \textbf{Mitigated Mode}: Evaluates the security invariants with proposed defenses enabled (\texttt{Fixed = TRUE}). A \textbf{PASS (0 errors)} result formally verifies that the mitigation eliminates the side channel across all schedules.
\end{itemize}

\subsection{Interpreting Diagnostic Counterexample Traces}
When a security invariant is violated in Mode B, TLC outputs the state space diameter, the total and distinct state counts, and the exact sequence of states leading to the violation.

For example, when checking the concurrent synchronization benchmark under Mode B, TLC explores 44 states (39 distinct states, diameter 5) and reports:
\begin{center}
    \texttt{Error: Invariant NoTimingLeak is violated.}
\end{center}
TLC then outputs a concrete 5-step diagnostic error trace:
\begin{enumerate}[label=\textbf{Step \arabic*:}, leftmargin=1.8cm, itemsep=0.15em, topsep=0.15em]
    \item \textbf{Initial Predicate}: TLC initializes state variables ($h = 0, \texttt{sem} = 1, t = 0, T_{\text{start}} = 0, t_{\text{prime}} = 0, v = 0, \texttt{out} = \langle \rangle, pc = \langle \text{"T1\_1"}, \text{"l0"} \rangle$).
    \item \textbf{Entry Point ($l_0$)}: Process $T_2$ executes statement $l_0$, recording entry timestamp $T_{\text{start}} = 0$, advancing clock to $t = 1$, outputting $\texttt{"c"}$ ($\texttt{out} = \langle \text{"c"} \rangle$), and transitioning $pc[2]$ to \text{"l1"}.
    \item \textbf{Branch Decision ($l_1$)}: Process $T_2$ evaluates secret $h = 0$. Since $h \neq 1$, it bypasses semaphore acquisition and transitions $pc[2]$ directly to $l_6$ with $t = 1$.
    \item \textbf{Skip Operation ($l_6$)}: Process $T_2$ executes \texttt{skip}, advancing clock to $t = 2$ and transitioning $pc[2]$ to exit point $l_7$.
    \item \textbf{Exit Point ($l_7$)}: Process $T_2$ executes $l_7$, recording exit timestamp $t_{\text{prime}} = 2$, advancing clock to $t = 3$, appending $\texttt{"d"}$ ($\texttt{out} = \langle \text{"c"}, \text{"d"} \rangle$), and transitioning $pc[2]$ to \text{"Done"}.
\end{enumerate}
At Step 5, the observer computes the elapsed duration:
\begin{equation}
    \Delta = t_{\text{prime}} - T_{\text{start}} = 2 - 0 = 2
\end{equation}
Because the secret branch was bypassed ($h = 0$), $T_2$ completed in only 2 ticks, whereas taking the branch ($h = 1$) requires acquiring \texttt{sem} and takes at least 4 ticks ($\Delta \ge 4$). Since $\Delta = 2 < \Delta_{\text{lo}}$, \texttt{NoTimingLeak} fails, providing the developer with an actionable, step-by-step witness of the timing channel.

\subsection{Mitigation Verification Workflow}
Once an error trace is extracted, candidate defenses (such as branch padding or memory barriers) are added to the specification, conditioned on a boolean configuration parameter (\texttt{Fixed = TRUE}). Re-running TLC under Mode B verifies that:
\begin{enumerate}[label=\arabic*., itemsep=0.15em, topsep=0.15em]
    \item The security invariant (\texttt{NoTimingLeak} or \texttt{NoOrderLeak}) passes with \textbf{0 errors}.
    \item The state space exploration confirms that execution metrics are equalized across all secret values, proving that the side channel has been eliminated.
\end{enumerate}

\section{Tools and Modeling Environment}
Our verification workflow uses PlusCal, TLA+, and TLC:
\begin{itemize}[itemsep=0.15em, topsep=0.15em]
    \item \textbf{PlusCal}: We wrote all benchmark models in PlusCal using its C-syntax dialect, following the practical modeling patterns outlined by Wayne~\cite{wayne2018practical}. PlusCal provides familiar imperative constructs (threads, loops, conditionals, and \texttt{await}) that compile directly into TLA+. In PlusCal, every label defines an atomic step boundary, allowing us to specify exactly where threads can interleave.
    \item \textbf{Temporal Logic of Actions (TLA+)}: TLA+ represents state transitions mathematically using unprimed variables for the current state and primed variables for the next state. This provides unambiguous semantics for every action.
    \item \textbf{TLC Model Checker}: TLC is an explicit-state model checker that visits all reachable states breadth-first. It checks safety invariants on each visited state and prints the shortest counterexample trace when an invariant fails.
    \item \textbf{Environment}: We ran TLC on Java 11 under macOS. Each benchmark has its own configuration file specifying constants, initial states, and invariant properties. We authored models in VS Code using the TLA+ extension and ran batch checks via the TLC command line.
\end{itemize}

\section{Scope and Practical Limitations}
We note the following boundaries and assumptions in our evaluation:
\begin{enumerate}[label=\arabic*., itemsep=0.15em, topsep=0.15em]
    \item \textbf{Manual Model Translation}: We manually translated the benchmark algorithms into PlusCal and selected observation points based on RWFM principles. Building an automated front-end parser to generate TLA+ directly from source code is an important next step.
    \item \textbf{Selective Information-Flow Concepts}: We used RWFM for practical point selection (tracking secret branches and shared variable writes) without implementing full multi-level lattice algebra.
    \item \textbf{Finite Bounded State Spaces}: Like all explicit-state checkers, TLC requires bounded parameters (e.g., single secret bits, fixed loops, and small numbers of threads). While this proves absence of leaks across all interleavings for the chosen bounds, it does not replace general inductive proofs for unbounded thread counts.
\end{enumerate}

\section{Benchmark 1: Concurrent Synchronization and Order Channels}

\subsection{Problem Context and Research Origin}
This benchmark investigates secret-dependent lock contention in multi-threaded programs, originating from the study by Ghosal and Shyamasundar~\cite{ghosal2021axiomatic}. Two concurrent threads $T_1$ and $T_2$ contend for a shared binary semaphore (\texttt{sem}) and mutate shared variable $v$. Thread $T_2$ conditionally accesses the critical section depending on a confidential secret $h \in \{0, 1\}$.

\subsection{PlusCal Algorithm and Model Specification}
Listing~\ref{lst:concurrent-leak} presents the formal PlusCal algorithm for the concurrent semaphore benchmark, modeled in \texttt{ConcurrentLeak.tla}. The specification models two concurrent threads $T_1$ and $T_2$ synchronizing via shared semaphore \texttt{sem} and variable $v$, instrumented with auxiliary clock variables ($t, T_{\text{start}}, t_{\text{prime}}$) to measure execution duration without altering program logic.

\subsection{Leakage Mechanism and Secret Variables}
The benchmark exhibits both timing and execution order side channels:
\begin{itemize}[itemsep=0.15em, topsep=0.12em]
    \item \textbf{Secret Variable}: $h \in \{0, 1\}$ (high confidentiality), governing whether $T_2$ enters the critical section.
    \item \textbf{Timing Side Channel}: When $h = 0$, $T_2$ bypasses the semaphore critical section and completes quickly ($\Delta = t_{\text{prime}} - T_{\text{start}} \le 3$). When $h = 1$, $T_2$ serializes behind $T_1$, waiting for the semaphore release and suffering an observable delay ($\Delta \ge 7$).
    \item \textbf{Output Order Channel}: Interleaving produces observable output traces in $\texttt{out}$. When $h = 1$, serialization forces the trace prefix $\langle \text{"a"}, \text{"c"}, \text{"d"}, \text{"b"} \rangle$, whereas when $h = 0$, $T_2$ can finish earlier, producing traces such as $\langle \text{"c"}, \text{"a"}, \text{"d"}, \text{"b"} \rangle$.
\end{itemize}

\subsection{Layered Invariants and Leaky Assertions Formulation}
Evaluated at the public exit statement $l_7$ where $\texttt{Observed} \triangleq (pc[2] = \text{"Done"})$ and $\Delta \triangleq t_{\text{prime}} - T_{\text{start}}$:
\begin{itemize}[itemsep=0.12em, topsep=0.1em]
    \item \textbf{Functional Invariants}: $\texttt{GlobalInv} \triangleq \texttt{sem} + (\text{if } pc[1] \in \text{T1Crit} \text{ then } 1 \text{ else } 0) + (\text{if } pc[2] \in \text{T2Crit} \text{ then } 1 \text{ else } 0) = 1$, and $\texttt{FunctionalPost} \triangleq (pc[1] = \text{"Done"} \land pc[2] = \text{"Done"}) \implies (v = 1 + 2h \land \texttt{sem} = 1)$.
    \item \textbf{Calibration Bounds}: $\texttt{Calib0} \triangleq (\texttt{Observed} \land h = 0) \implies \Delta \in [2, 7]$ and $\texttt{Calib1} \triangleq (\texttt{Observed} \land h = 1) \implies \Delta \in [4, 9]$.
    \item \textbf{Attacker Leaky Assertions}: $\texttt{LA\_Low} \triangleq (\texttt{Observed} \land \Delta < \Delta_{\text{lo}}) \implies (h = 0)$, $\texttt{LA\_High} \triangleq (\texttt{Observed} \land \Delta \ge \Delta_{\text{hi}}) \implies (h = 1)$, and $\texttt{LA\_Trace} \triangleq \texttt{ACDB} \implies (h = 0)$.
    \item \textbf{Security Invariant (Non-Interference)}: $\texttt{NoTimingLeak} \triangleq \texttt{Observed} \implies (\Delta \ge \Delta_{\text{lo}} \land \Delta < \Delta_{\text{hi}})$.
\end{itemize}

\subsection{TLC Model Configuration and Verification Metrics}
The TLC model configuration sets execution bounds: $\Delta_{\text{lo}} = 4$ and $\Delta_{\text{hi}} = 8$. In Mode~A, TLC verified all functional invariants and calibrated leaky assertions across all 44 reachable states (39 distinct states, diameter 5) in 571~ms with \textbf{0 violations}, certifying the mathematical soundness of the attacker's deductions.

In Mode~B, TLC checked security property \texttt{NoTimingLeak}. Because execution times differ between secret paths, TLC refuted the invariant and generated a diagnostic counterexample trace witnessing the vulnerability.

\subsection{How to Read and Interpret the TLC Diagnostic Trace}
When TLC detects a security invariant violation during breadth-first state exploration, it halts model checking and generates an execution counterexample trace witnessing the scheduling interleaving that leaks confidential information. For \texttt{ConcurrentLeak.tla} under configuration \texttt{ConcurrentLeak.cfg}, TLC explored the state space across 44 states (39 distinct states, search diameter 5 transitions) within 571~ms before reporting that invariant \texttt{NoTimingLeak} is violated.

A security engineer or verification analyst reading the resulting 5-state diagnostic counterexample trace interprets the system execution through the following operational stages:

\begin{itemize}[itemsep=0.25em, topsep=0.2em]
    \item \textbf{State 1 (Initial Predicate and Variable Bindings)}: TLC initializes the model under secret $h = 0$. Shared semaphore and synchronization variables are initialized to $\texttt{sem} = 1$ and $v = 0$. Extra auxiliary clocks begin at $t = 0$, $T_{\text{start}} = 0$, and $t_{\text{prime}} = 0$, while the public observable output trace is empty ($\texttt{out} = \langle \rangle$). Thread program counters are bound to $pc = \langle \text{"T1\_1"}, \text{"l0"} \rangle$, indicating that Thread~$T_1$ and Thread~$T_2$ are ready to execute.
    
    \item \textbf{State 2 (Public Entry Point Execution by Thread $T_2$)}: Thread~$T_2$ executes the entry statement at label $l_0$. TLC marks modified variables: Process~$T_2$ records the initial public timestamp $T_{\text{start}} := 0$, emits the first observable character into the output trace ($\texttt{out} := \langle \text{"c"} \rangle$), advances the global step clock $t := 1$, and updates its program counter to $pc[2] := \text{"l1"}$.
    
    \item \textbf{State 3 (Secret-Dependent Branch Evaluation)}: At label $l_1$, Thread~$T_2$ evaluates the conditional branch guard \texttt{if h = 1}. Because secret $h = 0$, the guard evaluates to \textbf{false}. $T_2$ branches directly to label $l_6$ (the \texttt{else} path), updating $pc[2] := \text{"l6"}$. This branch transition is critical: it entirely bypasses semaphore acquisition ($\texttt{sem}$) and the critical section contention where Thread~$T_1$ would otherwise force serialization.
    
    \item \textbf{State 4 (Bypass Action Execution)}: At label $l_6$, Thread~$T_2$ executes the dummy balancing action \texttt{skip}. The global clock increments to $t := 2$, and the program counter transitions to $pc[2] := \text{"l7"}$.
    
    \item \textbf{State 5 (Public Exit Point and Termination)}: Thread~$T_2$ reaches the exit public point at label $l_7$. It captures the termination clock $t_{\text{prime}} := 2$, appends public character $\text{"d"}$ to the output trace ($\texttt{out} := \langle \text{"c"}, \text{"d"} \rangle$), increments the global clock to $t := 3$, and terminates with $pc[2] := \text{"Done"}$. Crucially, Thread~$T_1$'s program counter remained frozen at $\text{"T1\_1"}$ throughout all five states, witnessing that preemptive scheduling allowed $T_2$ to complete without a single context switch to $T_1$.
\end{itemize}

\noindent\textbf{Deducing Confidential Secrets from the Diagnostic Trace}:
Upon reaching thread termination at State~5, the observation condition $\texttt{Observed} \equiv (pc[2] = \text{"Done"})$ becomes \textbf{true}. The observer computes the elapsed execution duration between the public observation points:
$$\Delta_{\text{obs}} = t_{\text{prime}} - T_{\text{start}} = 2 - 0 = 2 \text{ clock ticks}.$$
Because non-interference requires that thread execution time satisfies the calibrated safe bounds $\Delta \ge \Delta_{\text{lo}}$ (where $\Delta_{\text{lo}} = 4$ clock ticks), the security invariant \texttt{NoTimingLeak} evaluates to \textbf{FALSE}, exposing the timing leak. Conversely, TLC evaluates the attacker's calibrated leaky assertion:
$$\texttt{LA\_Low} \equiv (\texttt{Observed} \land \Delta_{\text{obs}} < 4) \implies (h = 0)$$
which evaluates to \textbf{TRUE}. By observing that $\Delta_{\text{obs}} = 2 < 4$, an external observer deduces secret $h = 0$ with 100\% mathematical certainty, demonstrating that the diagnostic trace provides complete operational proof of information leakage.

\section{Benchmark 2: Round-Robin Internal Timing Covert Channel}

\subsection{Problem Context and Research Origin}
This benchmark investigates internal timing channels governed by deterministic scheduling, originating from the foundational work by Russo and Sabelfeld~\cite{russo2006closing}. Secret-dependent branching in a multi-threaded system scheduled under round-robin time slicing shifts the interleaving turns between threads, altering the overall completion time of the program.

\subsection{Leakage Mechanism and Secret Variables}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Secret Variables}: $h \in \{0, 1\}$ (branch secret) and $h_2 \in \mathbb{N}$ (cryptographic accumulator).
    \item \textbf{Turn-Shift Timing Channel}: Thread $T_1$ contains an unbalanced branch: the $h = 1$ path requires 3 turns before assigning $l := 1$, whereas the $h = 0$ path requires only 2 turns. This turn shift alters when Thread $T_2$ executes, causing total execution time between \texttt{"START"} and \texttt{"END"} to vary: $\Delta = 8$ clock cycles when $h = 0$, and $\Delta = 9$ clock cycles when $h = 1$. An observer measuring total elapsed cycles directly deduces secret $h$.
\end{itemize}

\subsection{Leaky Assertions Formulation}
Evaluated upon thread termination (\texttt{Observed}): $\text{Calib0} \equiv (\text{Observed} \land h = 0) \implies (\Delta = 8)$, $\text{Calib1} \equiv (\text{Observed} \land h = 1) \implies (\Delta = 9)$, and $\text{LA\_Timing} \equiv \text{Observed} \implies ((\Delta \ge 9) \iff (h = 1))$. The non-interference security invariant checked to detect the leak is $\text{NoTimingLeak} \equiv \text{Observed} \implies (\Delta = 8)$.

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec} \quad \textbf{Constants}: $\Delta_{\text{lo}} = 8$, $\Delta_{\text{hi}} = 9$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}, \texttt{FunctionalPost}
    \item \textbf{Mode A (Soundness)}: \texttt{Calib0}, \texttt{Calib1}, \texttt{LA\_Timing}
    \item \textbf{Mode B (Leak Discovery)}: \texttt{NoTimingLeak}
\end{itemize}

\section{Benchmark 3: Branch-Padding Countermeasure and Constant-Time Execution}

\subsection{Problem Context and Research Origin}
This benchmark formalizes and verifies the branch-padding countermeasure proposed by Russo and Sabelfeld~\cite{russo2006closing} and extended by Mantel and Starostin~\cite{mantel2015timing}. The objective is to eliminate the internal timing covert channel identified in Benchmark~2 by equalizing branch step counts.

\subsection{Mitigation Mechanism and Balanced Control Flow}
In the vulnerable model, taking $h = 0$ consumed 2 scheduler turns while $h = 1$ consumed 3 turns. The transformed program introduces an auxiliary padding statement (\texttt{l4\_pad}) on the shorter branch path:
\begin{align*}
    \text{Thread } T_1 \text{ (Padded)} &: \quad \textbf{if } h = 1 \textbf{ then } [h_2 := 2 \cdot h_2 + l; \; \texttt{skip;}] \\
    &\quad\quad \textbf{else } [\texttt{skip; } \mathbf{skip; \; /* \; l4\_pad \; */}] \; l := 1; \; \texttt{print('1');}
\end{align*}
Inserting \texttt{l4\_pad} forces both execution paths to consume exactly 3 scheduler turns before reaching $l_5$, equalizing the execution duration to $\Delta = 9$ clock cycles across both $h = 0$ and $h = 1$.

\subsection{Leaky Assertions and Mitigation Invariants}
The mitigation enforces constant-time latency: $\text{ConstantTime} \equiv \text{Observed} \implies (\Delta = 9)$ and $\text{NoTimingLeak} \equiv \text{ConstantTime}$. The attacker's prior leaky assertion $\text{LA\_Timing} \equiv \text{Observed} \implies (\Delta \ge 9 \iff h = 1)$ is defeated (evaluates to \textbf{False} when $h = 0$ because $\Delta = 9$).

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec} \quad \textbf{Constants}: $\Delta_{\text{lo}} = 8$, $\Delta_{\text{hi}} = 9$
    \item \textbf{Invariants Checked}: \texttt{TypeOK}, \texttt{FunctionalPost}, \texttt{ConstantTime}, \\ \texttt{NoTimingLeak}
    \item \textbf{Outcome}: Evaluates to \textbf{PASS (0 errors)}, formally verifying that the timing channel is closed.
\end{itemize}

\section{Benchmark 4: Cryptographic Modular Exponentiation Side Channel}

\subsection{Problem Context and Research Origin}
This benchmark models algorithmic timing vulnerabilities in the square-and-multiply algorithm used for modular exponentiation ($y^K \pmod N$), foundational to RSA and Diffie--Hellman implementations. The vulnerability was first identified by Kocher~\cite{kocher1996timing} and framed axiomatically by Ghosal and Shyamasundar~\cite{ghosal2021axiomatic}.

\subsection{Leakage Mechanism and Secret Variables}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Secret Variable}: $K \in \text{Seq}(\{0, 1\})$ (cryptographic private key), $\text{HW}(K) \in 0..\text{BITS}$ (Hamming weight).
    \item \textbf{Timing Channel}: In each bit iteration, modular squaring is executed unconditionally. Modular multiplication is executed only when secret bit $K[i] = 1$. Total execution duration is $\Delta = \text{Len}(K) \cdot \text{SqCost} + \text{HW}(K) \cdot \text{MulCost}$. An external observer measuring elapsed duration directly learns the private key's Hamming weight.
\end{itemize}

\subsection{Leaky Assertions Formulation}
\begin{align*}
    \text{LeakyAssertion} &\equiv \text{Observed} \implies (\Delta \ge \text{Threshold} \iff \text{HW}(K) \ge \text{SecretThreshold}) \\
    \text{ConstantTime}   &\equiv \text{Observed} \implies (\Delta = \text{ExpectedConstantTime})
\end{align*}

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec} \quad \textbf{Constants}: $N = 15$, $Y_0 = 7$, $\text{BITS} = 4$, $\text{MulCost} = 3$, $\text{SqCost} = 2$, $\text{PrintCost} = 1$, $\text{Fixed} \in \{\text{FALSE}, \text{TRUE}\}$, $\text{Threshold} = 2$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}, \texttt{Correct}
    \item \textbf{Mode A (Soundness)}: \texttt{LeakyAssertion} \\ (evaluates \textbf{TRUE} under $\texttt{Fixed = FALSE}$)
    \item \textbf{Mode B (Leak Discovery)}: \texttt{ConstantTime} (refuted under $\texttt{Fixed = FALSE}$, confirmed under $\texttt{Fixed = TRUE}$)

\section{Benchmark 5: Web Authentication Latency Side Channel}

\subsection{Problem Context and Research Origin}
This benchmark models remote timing vulnerabilities in web authentication endpoints, based on the predictive timing mitigation framework of Askarov, Zhang, and Myers~\cite{askarov2010predictive}. The system handles user login by checking whether the username exists before executing cryptographic password verification.

\subsection{Leakage Mechanism and Secret Variables}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Secret Variables}: $\texttt{valid\_user} \in \{\text{TRUE}, \text{FALSE}\}$ (account existence), and\\ $\texttt{password\_match} \in \{\text{TRUE}, \text{FALSE}\}$ (password validity).
    \item \textbf{Timing Channel}: When a username does not exist ($\neg\texttt{valid\_user}$), the server immediately aborts after database lookup ($\Delta = \text{LookupCost} = 1$). When the username exists but the password fails, the server computes an expensive password hash ($\Delta = \text{LookupCost} + \text{HashCost} = 1 + 10 = 11$). Both paths emit the identical string \texttt{"error message"}, but response latency exposes whether the account exists.
\end{itemize}

\subsection{Leaky Assertions Formulation}
Evaluated at response point $l_{\text{exit}}$ where $\text{out}_{\text{err}} \equiv (\text{result} = \text{"error message"})$:
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item $\text{LA\_Time\_Low} \equiv (\neg\text{Fixed} \land \text{Observed} \land \text{out}_{\text{err}} \land \Delta \le 1) \implies (h = 0)$
    \item $\text{LA\_Time\_High} \equiv (\neg\text{Fixed} \land \text{Observed} \land \text{out}_{\text{err}} \land \Delta \ge 11) \implies (h = 1)$
    \item $\text{LA\_Timing} \equiv (\neg\text{Fixed} \land \text{Observed} \land \text{out}_{\text{err}}) \implies ((\Delta \ge 5) \iff (h = 1))$
    \item \textbf{Security Invariant}: $\text{NoTimingLeak} \equiv (\text{Observed} \land \text{out}_{\text{err}}) \implies (\Delta = 11)$
\end{itemize}

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec} \\
    \textbf{Constants}: $\text{LookupCost} = 1$, $\text{HashCost} = 10$, $\text{Threshold} = 5$, \\
    $\text{Fixed} \in \{\text{FALSE}, \text{TRUE}\}$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}, \texttt{FunctionalCorrect}
    \item \textbf{Mode A (Soundness)}: \texttt{Calib0}, \texttt{Calib1}, \texttt{LA\_Time\_Low}, \texttt{LA\_Time\_High}, and\\ \texttt{LA\_Timing}

\section{Benchmark 6: Persistent Memory Seqlock Under Power Failure}

\subsection{Problem Context and Research Origin}
This benchmark investigates information disclosure in non-volatile persistent memory (PM) architectures under power failure, based on the research by Graeme Smith~\cite{smith2026persistent}. The protocol models a Linux reader-writer seqlock managing confidential and public data records.

\subsection{Leakage Mechanism and Secret Variables}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Secret Variable}: $h \in \{0, 1\}$ ($h = 1$ is confidential high data; $h = 0$ is public low data).
    \item \textbf{Persistent State}: \texttt{pm\_x1} (data record), \texttt{pm\_x2} (classification flag), and \texttt{pm\_c} (sequence counter).
    \item \textbf{Crash-Reboot Leakage}: Stores commit asynchronously under weak persistency. If data ($x_1 := 1$) and counter ($c$) persist to PM while security tag ($x_2 := 1$) lags in volatile cache during a crash, post-reboot memory is inconsistent: $c$ is even (quiescent) and $x_2 = 0$ (marking low), yet $x_1 = 1$ (high secret). A post-reboot reader reads $x_2 = 0$ and emits high secret $1$ over the public channel.
\end{itemize}

\subsection{Leaky Assertions Formulation}
The security invariants are defined as $\text{LA\_PersistentLeak} \equiv (\neg\text{Fixed} \land \text{crashed} \land \text{ReaderDone} \land (\exists k : \text{out}[k] = 1)) \implies (h = 1)$ and $\text{NoInformationLeak} \equiv \forall k \in 1..\text{Len}(\text{out}) : (\text{out}[k] = 1) \implies (h = 0)$.

\subsection{TLC Model Configuration}
\begin{itemize}[itemsep=0.08em, topsep=0.08em]
    \item \textbf{Specification}: \texttt{SPECIFICATION Spec} \quad \textbf{Constants}: $\text{Fixed} \in \{\text{FALSE}, \text{TRUE}\}$
    \item \textbf{Functional Invariants}: \texttt{TypeOK}
    \item \textbf{Mode A (Soundness)}: \texttt{LA\_PersistentLeak}
    \item \textbf{Mode B (Leak Discovery)}: \texttt{NoInformationLeak}
\end{itemize}

\chapter{CONCLUSION AND FUTURE WORK}

\section{Conclusion}
This thesis provides a verification methodology for detecting information leakage and side-channel vulnerabilities in concurrent programs using TLA+. We provide executable invariants for leaky assertions, which enables verification of these properties through automated proof. Evaluation on 6 benchmarks showed that employing a 3-layered invariant structure with two modes of verification within TLC provides useful results:
\begin{itemize}[itemsep=0.25em, topsep=0.2em]
    \item \textbf{In Mode A}: We formally prove that, in all possible thread interleavings, given certain public observations (time-intervals, or sequences of events) the attacker can make correct deductions about the secret value in all cases, with no violations.
    \item \textbf{In Mode B}: We disprove non-interference properties and automatically generate explicit counter-example traces. These traces clearly show what thread orders and synchronisation delays caused information leakage in the program.
\end{itemize}
Finally, we verified that mitigations in software (branch padding, constant-time operations, and purging of caches in persistent memory) successfully remove side-channel vulnerabilities in all possible execution paths.

\section{Future Work}
The identification of observation points, insertion of atomic step annotations and leaky assertions in this work is performed manually. Future work involves \textbf{automation} of this verification and mitigation pipeline:

\begin{enumerate}[label=\arabic*., itemsep=0.35em]
    \item \textbf{Automatic Translation of Source Code to PlusCal}:
    Develop an automated front-end (such as Clang/LLVM for C/C++, or Soot for Java) to translate concurrent source code. Each statement should be translated to corresponding actions in PlusCal, preserving atomicity annotations. Non-intrusive extra clocks ($t, T_{\text{start}}, t'$) and observable traces are inserted.

    \item \textbf{Automatic Leaky Assertion Synthesis}:
    Use static taint analysis and symbolic execution to automatically infer information flow from annotated secret variables to shared synchronisation. Observation points vulnerable to leaks can be identified, calibration intervals determined, and leaky assertions generated automatically.

    \item \textbf{Counterexample-Guided Automated Repair}:
    Develop tools to automatically parse error traces from TLC and synthesise targeted fixes. Cycle balancing branch padding or persistent memory fence instructions may be inserted into the source code.
\end{enumerate}
